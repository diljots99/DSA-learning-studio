BFundamental understanding

What is the two-pointer technique?

A pointer here is not a memory address. It is an integer index (or a reference to a node) that marks a position in a sequence. The technique keeps two such positions and moves them according to the values they currently see. The USACO Guide describes it as iterating two pointers across an array to track indices that satisfy some condition [1]. Purdue's competitive-programming course gives the same definition: maintain two indices into one array or two arrays, and move them based on the values they point to [3].

Formal definition A two-pointer algorithm over sequences of total length n keeps a state (p, q) of two positions, plus O(1) extra variables. At each step it examines the elements at p and q and advances at least one pointer monotonically: each pointer only ever moves in one fixed direction. Because each pointer can move at most n times, the loop runs O(n) times. Correctness rests on an invariant: every position a pointer has passed over can no longer be part of an answer that has not already been found. Laaksonen's Competitive Programmer's Handbook treats the method as a case of amortized analysis for exactly this reason: both pointers move in one direction only, which keeps the total work linear [2].
Plain-English definition Put one finger on each of two places in a list. Look at what is under your fingers, decide which finger is "stuck" on a hopeless value, and slide that finger along. Never slide a finger backwards. When your fingers meet or fall off the end, you are done. Every slide throws away a possibility you can prove was useless.

Why the technique exists

Many array and string questions are about pairs: two values that add up to a target, two walls that hold the most water, two characters that must match, one item from each of two lists. There are n(n−1)/2 pairs among n items, so checking them all is quadratic. Purdue's slides make the point with Container With Most Water: the obvious solution tries all pairs in O(n²), while two pointers moving inward from both ends solve it in linear time [3]. The technique exists to prune the pair space without missing the answer.

What came before, and where the idea comes from

The technique has no single inventor. It is a pattern that runs through classical algorithms, and you have probably used it already:

  • Merging two sorted arrays, the core of mergesort, walks one index through each input and repeatedly copies the smaller front element, in linear time [6][7].
  • Quicksort partitioning scans index i from the left and index j from the right, swapping out-of-place items until the pointers cross [4][5].
  • Dijkstra's Dutch National Flag problem, a structured-programming exercise in program derivation and proof, partitions items of three colours in one pass with three indices [10][11][17].
  • Floyd's "tortoise and hare" cycle-finding algorithm moves two pointers at different speeds through a sequence. Knuth credited the idea to Robert W. Floyd, though the attribution is disputed [12][13].

Interview culture later gave the shared idea a name, "two pointers". Competitive-programming references now teach it as a technique in its own right [1][2][3].

CThe problem statement

We anchor the chapter on the canonical problem, pair sum in a sorted array, and then generalise. It appears as LeetCode 167 "Two Sum II", in CSES "Sum of Two Values" and in Laaksonen's handbook as the 2SUM problem [2][1][23].

Problem: PAIR-SUM (sorted) Input: a list A[0..n−1] of integers sorted in non-decreasing order, and a target T.
Output: indices i < j with A[i] + A[j] = T, or "none".
Constraints (typical): n up to 10⁵–10⁶; extra memory should be O(1); each element may be used at most once.

Why the naive approach is inefficient

The brute-force solution tests every pair, for i … for j > i, which is n(n−1)/2 = Θ(n²) checks in the worst case. Our own measurement in Section I gives 499,500 pair checks for n = 1000. For n = 10⁶ that is about 5 × 10¹¹ checks, which takes minutes to hours even in a compiled language and far longer in Python. Illustration

How two pointers improves the solution

Put lo at the smallest value and hi at the largest, and look at s = A[lo] + A[hi]:

  • If s < T, then A[lo] paired with the largest remaining value is still too small, so it is too small with every remaining partner. Discard it: lo += 1.
  • If s > T, then A[hi] paired with the smallest remaining value is still too big, so discard it: hi -= 1.
  • If s = T, we are done.

Each step removes one element from consideration, so there are at most n − 1 steps. The Purdue slides note that the loop runs while first < second, so no element is used twice, and that each step moves one pointer, so the run time is linear [3]. Including an initial sort, the total is O(n log n), which matches the USACO Guide's analysis [1][2].

Real-world analogy: buying two gifts with an exact budget Lay price tags on a table, cheapest on the left and most expensive on the right. Pick up the cheapest and the most expensive. Too expensive together? The expensive one can't work even with the cheapest item, so put it back. Too cheap? The cheap one can't reach the budget even with the most expensive item, so put it back. Every "put back" is permanent, and you never reconsider a tag. You finish after at most one look per tag. Illustration

FInternal working

Memory representation: what a "pointer" really is in Python

In CPython a list is a variable-length array: a contiguous block of references to other objects, plus a header that stores the length. That is why indexing a[i] takes constant time, independent of i and of the list's length [25][18]. A two-pointer "pointer" is just a Python int used as an index into that block. Moving it (lo += 1) is O(1), and reading a[lo] is O(1). This random access is what converging pointers need, because they must reach the right end immediately.

Execution flow of the converging loop

State changes, step by step (pair sum)

  1. Initialise lo = 0, hi = n − 1. The window holds the whole array. For n ≤ 1 the loop never runs and we return None.
  2. Read A[lo] and A[hi]: two O(1) index operations.
  3. Compute s = A[lo] + A[hi]. Python ints are arbitrary precision, so there is no overflow. In C or Java, use 64-bit arithmetic or compare A[lo] with T − A[hi] instead.
  4. Decide with one three-way comparison against T.
  5. Mutate exactly one pointer, by ±1. Nothing else changes, and the array itself is never modified.
  6. Re-test the loop condition lo < hi. When it fails, the window contains fewer than two elements, so no pair remains.

GMathematical foundation

G.1 Correctness of converging pair-sum (loop invariant)

Invariant I Before every iteration: if some pair (i*, j*) with i* < j* and A[i*] + A[j*] = T exists, then there is one with lo ≤ i* < j* ≤ hi.

Initialisation. lo = 0 and hi = n−1, so every pair is inside the window.

Maintenance. Suppose s = A[lo] + A[hi] < T. For any k with lo < k ≤ hi, sortedness gives A[k] ≤ A[hi], so

A[lo] + A[k] ≤ A[lo] + A[hi] < T.

So lo pairs successfully with no index in the window, and removing it (lo ← lo + 1) keeps I true. The case s > T is symmetric: for any k with lo ≤ k < hi, A[k] + A[hi] ≥ A[lo] + A[hi] > T, so we can remove hi.

Termination. The variant Φ = hi − lo starts at n − 1 and drops by exactly 1 per iteration that does not return. When lo ≥ hi, the window holds no pair, so by I no solution existed and returning "none" is correct. If we return early, the returned pair is correct by construction. ∎

This is the formal version of the matrix picture in Figure D.2. Each comparison removes a row (index lo) or a column (index hi) of the upper-triangular sum matrix, and the rows and columns are sorted. The same staircase argument underlies searching a row- and column-sorted matrix in O(m+n). Illustration

G.2 The amortized (monotone-pointer) bound

For the same-direction and two-sequence families, the loop body may not move both pointers every time, so "Φ drops by one" is replaced by a counting argument. Each pointer only increases and never exceeds its sequence length, so the total number of increments is at most n per pointer. Laaksonen gives this argument for the subarray-sum example: the left pointer moves O(n) steps in total and the right pointer, which only moves to the right, also moves O(n) steps, so the algorithm is O(n) even though one iteration may move a pointer many times [2]. The USACO Guide uses the same reasoning for its sliding-window example: both pointers move at most N times, so the total is O(N) [1].

total work = Σiterations (pointer moves + O(1)) ≤ (np + nq) + O(#iterations) = O(n)

G.3 Container With Most Water: why moving the shorter wall is safe

Let area(i, j) = (j − i) · min(hi, hj). Suppose hlo ≤ hhi. For any k with lo < k < hi:

area(lo, k) = (k − lo) · min(hlo, hk) ≤ (k − lo) · hlo < (hi − lo) · hlo = area(lo, hi).

Every container that keeps wall lo and is narrower than the current one is strictly worse than the current one, which we have already recorded. So lo can be dropped without losing the optimum. Purdue's slides state exactly this insight: any container [i, k] inside [i, j] holds no more than the current container when h[i] is the shorter wall [3].

G.4 Dutch National Flag invariant

With pivot class "1", Dijkstra's three-way partition keeps four zones. Sedgewick and Wayne state the invariant as: a[lo..lt−1] less than v, a[lt..i−1] equal to v, a[i..gt] not yet examined, and a[gt+1..hi] greater than v [4][5]. Each iteration either advances i or decreases gt, so the unknown zone gt − i + 1 shrinks by one every time. That gives at most n iterations, a single pass, and Θ(n) examinations [10].

G.5 Floyd's cycle detection: why the pointers meet, and where

Iterate xk+1 = f(xk) on a finite set. The sequence eventually repeats: a tail of length μ leads into a cycle of length λ [12]. The tortoise is at xk and the hare at x2k. They coincide exactly when k ≥ μ and λ divides k, and the first such k is at most μ + λ [14]. If the meeting happens a steps into the cycle, then μ + a = k is a multiple of λ. So walking μ more steps from the meeting point lands on the entrance, and that is why phase 2 restarts one pointer at x0 and moves both at speed 1 [12]. The algorithm uses O(λ + μ) steps and O(1) memory [12].

Reading the notations

For converging pair-sum the worst-case running time is Θ(n). It is O(n) because Φ bounds the iterations, and it is Ω(n) because with no solution every element must be discarded one at a time. The best case is Θ(1). So the tightest statement valid for all inputs is O(n), and Ω(1) is the matching lower bound. A stronger fact also holds: any correct algorithm must look at Ω(n) elements in the worst case, because an unread element could complete the target. Two pointers are therefore asymptotically optimal for sorted pair-sum. Illustration

Recurrences? Amortization?

Two-pointer loops are iterative, so no recurrence is needed. Their analysis is an aggregate amortized argument: one iteration of a sliding-window loop may move lo many times, but the total over the whole run is at most n, so the average cost per iteration is O(1) [2]. Recurrences appear only when two pointers is used inside divide and conquer. Mergesort's T(n) = 2T(n/2) + Θ(n) has a linear two-pointer merge as its Θ(n) term, which gives Θ(n log n) overall [7].

Time–space trade-offs and theory versus Python

  • Sort + two pointers versus hashing. On unsorted data, a one-pass hash map solves pair-sum in expected O(n) time with O(n) memory. Sorting first costs O(n log n) time, and the pointer phase then needs only O(1) extra memory. The sort itself either mutates the caller's list (list.sort()) or copies it (sorted()) [19]. Dict and set operations are O(1) on average but O(n) in the worst case [18].
  • Constant factors in CPython. Each lo += 1 creates or reuses an int object and runs bytecode, so a two-pointer loop in pure Python does roughly 10⁷ simple steps per second. Built-ins written in C (sorted, list.reverse, s[::-1], heapq.merge's internals) are much faster per element. For example, s == s[::-1] is often faster than a hand-written palindrome loop even though it allocates O(n) extra memory. Big-O predicts growth, not wall-clock winners at small n. Illustration
  • Slicing is not free. a[i:j] copies j − i references and x in list is O(n) [18]. Writing if target - a[i] in a[i+1:] inside a loop silently turns a "two pointer" solution back into O(n²).
  • list.pop(0) and insert(0, x) are O(n) [18]. Moving an index is the O(1) way to "remove from the front".

I.1 Converging pointers: pair sum (with an optional trace)

def pair_sum_sorted(nums: List[int], target: int,
                    trace: bool = False) -> Optional[Tuple[int, int]]:
    """Return indices (i, j), i < j, with nums[i] + nums[j] == target.
    Precondition: nums is sorted in non-decreasing order.  O(n) time, O(1) space."""
    lo, hi = 0, len(nums) - 1
    step = 0
    while lo < hi:                          # window [lo..hi] still has >= 2 items
        s = nums[lo] + nums[hi]
        step += 1
        if trace:
            print(f"step {step}: lo={lo} hi={hi} sum={nums[lo]}+{nums[hi]}={s}", end="  ")
        if s == target:
            if trace: print("-> FOUND")
            return lo, hi
        if s < target:                      # nums[lo] is too small for EVERY partner
            if trace: print("-> too small, lo += 1")
            lo += 1
        else:                               # nums[hi] is too big for EVERY partner
            if trace: print("-> too big, hi -= 1")
            hi -= 1
    return None

Line by line. lo, hi = 0, len(nums) - 1 opens the window over the whole list (for an empty list, hi = −1 and the loop is skipped). while lo < hi requires two distinct indices, so an element is never paired with itself. s < target ⇒ lo += 1 and s > target ⇒ hi -= 1 are the two elimination steps proved in G.1. Returning a tuple of indices (rather than values) matches LeetCode 167's contract, apart from its 1-based indexing [23].

I.2 Converging pointers on strings and greedy variants

def is_palindrome(s: str) -> bool:
    """LeetCode 125: ignore non-alphanumerics, compare case-insensitively. O(n), O(1)."""
    lo, hi = 0, len(s) - 1
    while lo < hi:
        if not s[lo].isalnum():
            lo += 1
        elif not s[hi].isalnum():
            hi -= 1
        elif s[lo].lower() != s[hi].lower():
            return False
        else:
            lo += 1
            hi -= 1
    return True

def reverse_in_place(a: list) -> None:
    """Swap symmetric pairs until the pointers meet. floor(n/2) swaps."""
    lo, hi = 0, len(a) - 1
    while lo < hi:
        a[lo], a[hi] = a[hi], a[lo]
        lo += 1
        hi -= 1

def max_area(height: List[int]) -> int:
    """LeetCode 11, Container With Most Water. O(n), O(1)."""
    lo, hi = 0, len(height) - 1
    best = 0
    while lo < hi:
        width = hi - lo
        best = max(best, width * min(height[lo], height[hi]))
        if height[lo] < height[hi]:         # the shorter wall limits every narrower
            lo += 1                         # container that keeps it -> discard it
        else:
            hi -= 1
    return best

str.isalnum() returns true only for letters and digits, and str.lower() gives a case-insensitive comparison [20]. Note the if / elif chain: each iteration moves at least one pointer, which guarantees progress. In max_area the comparison height[lo] < height[hi] decides which wall is provably useless (G.3). On ties either pointer may move.

I.3 Anchor + converging: 3Sum

def three_sum(nums: List[int]) -> List[List[int]]:
    """LeetCode 15: all unique triplets summing to 0. O(n^2) time, O(1) extra
    besides the output and the sort."""
    a = sorted(nums)                        # Timsort: O(n log n)
    n = len(a)
    out = []
    for i in range(n - 2):
        if a[i] > 0:                        # smallest of the three is positive -> stop
            break
        if i > 0 and a[i] == a[i - 1]:      # skip duplicate anchors
            continue
        lo, hi = i + 1, n - 1
        while lo < hi:
            s = a[i] + a[lo] + a[hi]
            if s < 0:
                lo += 1
            elif s > 0:
                hi -= 1
            else:
                out.append([a[i], a[lo], a[hi]])
                lo += 1
                hi -= 1
                while lo < hi and a[lo] == a[lo - 1]:   # skip duplicate seconds
                    lo += 1
    return out

Why only lo skips duplicates: once a triplet is recorded we move both pointers. If a[lo] now repeats, the sum with the same anchor can only be zero again with the same a[hi] value, so skipping repeated lo values is enough to prevent duplicate triplets. The randomized test compares the output, as a list, against a set built from itertools.combinations, so any duplicate would fail.

I.4 Same-direction pointers: reader/writer and fast/slow

def remove_duplicates(nums: List[int]) -> int:
    """LeetCode 26: in a sorted list keep the first copy of each value.
    Returns k; nums[:k] holds the unique values. O(n), O(1)."""
    if not nums:
        return 0
    write = 1                               # nums[:write] is the de-duplicated prefix
    for read in range(1, len(nums)):
        if nums[read] != nums[write - 1]:   # a value we have not kept yet
            nums[write] = nums[read]
            write += 1
    return write

def move_zeroes(nums: List[int]) -> None:
    """LeetCode 283: move zeros to the end, keep the order of non-zeros."""
    write = 0
    for read in range(len(nums)):
        if nums[read] != 0:

def find_duplicate(nums: List[int]) -> int:
    """LeetCode 287 via Floyd's tortoise and hare. nums has n+1 values in 1..n.
    Treat i -> nums[i] as a linked list; the duplicate is the cycle entrance."""
    slow = fast = nums[0]
    while True:                             # phase 1: meet inside the cycle
        slow = nums[slow]
        fast = nums[nums[fast]]
        if slow == fast:
            break
    slow = nums[0]                          # phase 2: find the entrance (mu)
    while slow != fast:
        slow = nums[slow]
        fast = nums[fast]
    return slow

def merge_sorted(a: List[int], b: List[int]) -> List[int]:
    """Merge two sorted lists into a new sorted list. Theta(len(a)+len(b))."""
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:                    # '<=' keeps the merge stable
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    out.extend(a[i:])                       # at most one of these is non-empty
    out.extend(b[j:])
    return out

def intersect_sorted(a: List[int], b: List[int]) -> List[int]:
    """Common values of two sorted lists (with multiplicity), O(len(a)+len(b))."""
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            out.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return out

def is_subsequence(s: str, t: str) -> bool:
    """LeetCode 392: can s be obtained from t by deleting characters?"""
    i = 0
    for ch in t:
        if i < len(s) and s[i] == ch:
            i += 1
    return i == len(s)

def sort_colors(nums: List[int]) -> None:
    """LeetCode 75. Invariant: [0,lt) == 0, [lt,i) == 1, [i,gt] unknown, (gt,n) == 2."""
    lt, i, gt = 0, 0, len(nums) - 1
    while i <= gt:
        if nums[i] == 0:
            nums[lt], nums[i] = nums[i], nums[lt]
            lt += 1; i += 1
        elif nums[i] == 2:
            nums[gt], nums[i] = nums[i], nums[gt]
            gt -= 1                         # do NOT advance i: the swapped-in value is unexamined
        else:
            i += 1

merge_sorted uses <= so that equal keys from a come before those from b. This is the stability property that makes mergesort stable. Only one of the final extend calls adds anything. In sort_colors the asymmetry is deliberate: after swapping with gt the incoming value has not been examined, so i stays where it is.

I.7 Error handling and input validation

Library-quality code should check its preconditions, because a converging search on unsorted input fails silently by returning a wrong "none". An O(n) check keeps the overall bound linear:

def checked_pair_sum(nums: List[int], target: int) -> Optional[Tuple[int, int]]:
    """Pair sum that refuses unsorted input instead of silently failing."""
    if not isinstance(nums, list):
        raise TypeError("nums must be a list")
    if any(nums[k] > nums[k + 1] for k in range(len(nums) - 1)):   # O(n) check
        raise ValueError("pair search with converging pointers requires sorted input")
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return lo, hi
        if s < target:
            lo += 1
        else:
            hi -= 1
    return None

Choosing between sort + two pointers and hashing

For 3Sum, Sedgewick and Wayne's ThreeSumFast sorts and then binary-searches for the third value, which costs n² log n [8]. Replacing the binary search with a two-pointer scan gives O(n²) [9][2]. A hash-set approach is also O(n²) but needs O(n) memory and makes de-duplicating triplets awkward. Sorting groups equal values together, so duplicates are skipped by comparing neighbours. Rule of thumb: if the output is about values and sorting is allowed, sort + two pointers. If it is about original positions in unsorted data, hashing.

When two pointers is the wrong tool

  • The data is unsorted and you are not allowed to reorder it or lose index information.
  • The predicate is not monotone. Moving a pointer must never be able to make a discarded position useful again. Sliding-window sums break with negative numbers for exactly this reason.
  • The structure only supports forward traversal (a singly linked list or a stream). Converging pointers need access from both ends, though same-direction variants still work.
  • Many queries against the same data, where precomputation (prefix sums, a sorted index plus binary search) pays off.

5. Missing duplicate skips (3Sum returns repeated triplets)

Without if i > 0 and a[i] == a[i-1]: continue, input [-1, -1, 0, 1, 2] reports [-1, 0, 1] twice. Without the inner skip, [-2, 0, 0, 2, 2] reports [-2, 0, 2] twice. Run both inputs in Lab 7 and watch the red "skip" frames.

6. Complexity misconceptions

  • "Two pointers is always O(n)." Only the pointer phase is. With a sort it is O(n log n), and 3Sum is O(n²) because the pointer phase runs n times [9].
  • "A while inside a for means O(n²)." Not for monotone pointers: the inner pointer's moves are counted over the whole run, not per outer iteration [2].
  • "Slicing is free." s[lo:hi+1] == s[lo:hi+1][::-1] in a loop copies O(n) characters every time [18].

7. Boundary errors in reader/writer

Starting write at 0 instead of 1 in remove_duplicates compares with nums[-1], the last element in Python, which is a silent wrong answer rather than an exception. Returning write - 1 instead of write is the other classic off-by-one. Invariant-first thinking prevents both: "nums[:write] is the answer so far" pins down both the initial value and the return value.

8. Interview mistakes

  • Jumping to code without stating why a pointer may move. Interviewers look for the elimination argument (Section G).
  • Not asking whether the input is sorted, whether values repeat, whether indices or values should be returned, and whether the input may be mutated.
  • Sorting when the problem needs original indices (LeetCode 1), or using a hash map when O(1) space was requested (LeetCode 167).
  • Not testing the empty input, a single element, all-equal values and the no-answer case.

Hint 1The largest square is at one of the two ends (most negative or most positive).
Hint 2Fill the output from the last index backwards with the larger of the two end squares.
Solution 
def sorted_squares(nums: List[int]) -> List[int]:
    """LeetCode 977: squares of a sorted array, in sorted order. O(n)."""
    n = len(nums)
    out = [0] * n
    lo, hi = 0, n - 1
    for k in range(n - 1, -1, -1):          # fill from the back with the larger square
        if abs(nums[lo]) > abs(nums[hi]):
            out[k] = nums[lo] * nums[lo]
            lo += 1
        else:
            out[k] = nums[hi] * nums[hi]
            hi -= 1
    return out

Each iteration places one value and moves one pointer: Θ(n) time, plus O(n) for the output. Squaring first and then sorting costs O(n log n).

Easy — 88. Merge Sorted Array (in place)

HintMerging from the front would overwrite unread values of nums1. The free space is at the back.
Solution 
def merge_into(nums1: List[int], m: int, nums2: List[int], n: int) -> None:
    """LeetCode 88: nums1 has length m+n (last n slots are padding).
    Fill from the BACK so nothing unread is overwritten. O(m+n), O(1)."""
    i, j, k = m - 1, n - 1, m + n - 1
    while j >= 0:                       # once nums2 is used up, nums1's rest is in place
        if i >= 0 and nums1[i] > nums2[j]:
            nums1[k] = nums1[i]; i -= 1
        else:
            nums1[k] = nums2[j]; j -= 1
        k -= 1

The loop runs while nums2 has elements left. Once it is empty, the rest of nums1 is already in place. O(m+n) time, O(1) space.

Medium — 16. 3Sum Closest

HintIt is the same skeleton as 3Sum. Instead of collecting exact hits, track the sum with the smallest |s − target|, and move pointers by comparing s with target.
Solution 
def three_sum_closest(nums: List[int], target: int) -> int:
    """LeetCode 16. O(n^2)."""
    a = sorted(nums)
    best = a[0] + a[1] + a[2]
    for i in range(len(a) - 2):
        lo, hi = i + 1, len(a) - 1
        while lo < hi:
            s = a[i] + a[lo] + a[hi]
            if abs(s - target) < abs(best - target):
                best = s
            if s < target:
                lo += 1
            elif s > target:
                hi -= 1
            else:
                return s                # cannot get closer than exact
    return best

O(n²) time and O(1) extra space besides the sort. Why is moving safe? If s < target, any smaller hi gives an even smaller sum, which is farther from target, so lo must increase. This is G.1's argument again.

Hard — 42. Trapping Rain Water

Hint 1Water above bar k is min(maxLeft(k), maxRight(k)) − h[k].
Hint 2If h[lo] < h[hi], then some bar on the right is at least as tall as anything we need, so the water at lo depends only on left_max.
Solution 
def trap(height: List[int]) -> int:
    """LeetCode 42, Trapping Rain Water. O(n) time, O(1) space."""
    lo, hi = 0, len(height) - 1
    left_max = right_max = 0
    water = 0
    while lo < hi:
        if height[lo] < height[hi]:
            left_max = max(left_max, height[lo])
            water += left_max - height[lo]
            lo += 1
        else:
            right_max = max(right_max, height[hi])
            water += right_max - height[hi]
            hi -= 1
    return water

Correctness: the water above bar lo is min(maxLeft, maxRight) − height[lo]. Claim: whenever we process lo, left_max ≤ maxRight, so the minimum is left_max. Why: left_max is the height of some bar p ≤ lo. When lo stood at p, we chose to process the left side, so height[p] < height[hi′] for the hi′ of that moment. Since hi only moves left, hi′ is still on the right of the current lo, which gives maxRight ≥ height[p] = left_max. The right side is symmetric. O(n) time and O(1) space, versus O(n) space for the two-prefix-array method. Verified against the definition on 3,000 random inputs in the module.

NAdvanced concepts

N.1 From 2-sum to k-sum

Fixing anchors and recursing turns k-sum into O(nk−1) time with two pointers at the bottom level (4Sum, LeetCode 18, is O(n³)). Whether 3SUM can be solved substantially faster than quadratic was a famous question. Gajentaan and Overmars (1995) defined 3SUM-hardness: a subquadratic algorithm for such a problem would give one for 3SUM, and many computational-geometry problems turn out to be 3SUM-hard [9]. The conjecture that 3SUM needs about n² time was refuted in 2014, when Grønlund and Pettie gave a slightly subquadratic algorithm [9]. Laaksonen's handbook notes the same 2014 result [2]. The gains are only logarithmic-factor improvements, so in practice the sort + two-pointer O(n²) algorithm remains the standard.

N.2 Monotone predicates: the bridge to sliding windows

Same-direction pointers [l, r] generalise to: "for each r, find the smallest l such that the window is valid". This is linear whenever validity is monotone: if [l, r] is valid, so is every [l′, r] with l′ ≥ l. Laaksonen's subarray-sum example and the USACO Books problem are of this form [2][1], and Purdue's slides point out that the sliding window applies when the window's validity is monotone [3]. The Sliding Window chapter develops this family in full. Here it is enough to see that it is the same monotone-pointer argument as G.2.

N.3 Partitioning: Hoare, Lomuto, 3-way and dual-pivot

Quicksort's partition is a converging two-pointer loop. Princeton's version scans i right while a[i] < v and j left while a[j] > v, swaps, and stops when they cross. Stopping on keys equal to the pivot is crucial to avoid quadratic time on inputs with many duplicates [4]. Dijkstra's 3-way partition (Lab 6, generalised to any pivot v) makes quicksort entropy-optimal on inputs with many repeated keys [4][5]. Princeton's demos also show Bentley–McIlroy 3-way partitioning and dual-pivot partitioning, the latter with yet more pointers [5]. CLRS presents the single-pointer Lomuto-style PARTITION alongside mergesort's two-pointer MERGE [22].

N.4 Cycle detection beyond linked lists

Floyd's method works for any iterated function on a finite set, not only for linked lists. That is why it can measure the period of a pseudorandom generator, as in Princeton's COS 126 assignment on linear congruential generators [13], and why it powers Pollard's rho factorisation [12]. Alternatives such as Brent's algorithm also use O(1) memory but need fewer function evaluations [12].

N.5 Many sequences and external memory

With k sorted inputs, a pointer per input plus a min-heap of the current fronts merges them in O(N log k). This is heapq.merge in Python [21], and it is the core of external mergesort and of merge-join plans in databases [15]. Postings-list intersection is further sped up with skip pointers, extra links that let a cursor jump ahead several entries when the other list's docID is far away [16].

N.6 Two pointers on two-dimensional data

A matrix whose rows and columns are both sorted supports a "staircase" search from the top-right corner. Each comparison discards a full row or column, so it takes O(m + n). It is exactly the converging argument of Figure D.2 applied to an explicit matrix. Illustration (LeetCode 240).

Practical engineering scenario

Two services each export a sorted stream of user IDs (tens of millions of lines each, too large to load into memory together). You need the sorted list of distinct IDs that appear in either export, streamed to a file. Design the algorithm, give its time and memory cost, and implement the core as a Python generator. What changes if there are 50 exports instead of 2?

Answers

Conceptual 1 — invariant

"If a valid pair exists, one lies entirely within [lo..hi]." It depends on the array being sorted. That is what makes A[lo] + A[hi] < T imply A[lo] + A[k] < T for all k ≤ hi, so lo can be discarded (symmetrically for hi). See G.1.

Conceptual 2 — reader/writer bound

The loop is driven by read, which advances exactly once per iteration, so there are n iterations, each O(1). write only increases and never exceeds read, so its total moves are also ≤ n. That is the aggregate (monotone-pointer) argument of G.2 [2].

Conceptual 3 — taller wall

The area is capped by the shorter wall. Discarding a wall is only safe if every unevaluated pair that uses it is provably no better (G.3). That proof works for the shorter wall: any narrower container keeping it has height ≤ the short wall and smaller width. For the taller wall it fails, because pairs that keep the taller wall but drop the short one can be taller. Smallest counterexample: [1, 3, 3]. Both rules first evaluate (0, 2) = 2 × 1 = 2. "Move the taller wall" then sets hi = 1, evaluates (0, 1) = 1, and stops with 2. The optimum is (1, 2) = 1 × 3 = 3. Moving the shorter wall goes to (1, 2) and finds 3. (Found by brute-force search over random inputs; verify it in Lab 4.)

Conceptual 4 — hash map vs two pointers

Prefer hashing when (a) the input is unsorted and you must return original indices (sorting destroys them unless you sort index pairs), or (b) the data arrives as a stream and you want a single pass without sorting. Prefer two pointers when the input is already sorted or memory is tight: O(1) extra space and worst-case (not just expected) O(n) [18].

Conceptual 5 — Floyd phase 2

At the meeting point, the tortoise has walked μ + a steps, which is a multiple of λ. So μ further steps from the meeting point land on the cycle entrance. A pointer starting at x₀ also reaches the entrance after exactly μ steps. Moving both at speed 1, they first coincide at the entrance [12].

Coding 1 — count pairs below target 
def count_pairs_less(nums: List[int], target: int) -> int:
    """LeetCode 2824: number of pairs i<j with nums[i]+nums[j] < target.
    Sorting does not change the answer (pairs are unordered). O(n log n)."""
    a = sorted(nums)
    lo, hi = 0, len(a) - 1
    count = 0
    while lo < hi:
        if a[lo] + a[hi] < target:
            count += hi - lo            # a[lo] works with EVERY partner in lo+1..hi
            lo += 1
        else:
            hi -= 1
    return count

Key step: if a[lo] + a[hi] < target, then a[lo] works with every index in lo+1..hi (they are all ≤ a[hi]), so add hi − lo at once. Sorting is allowed because the answer counts unordered pairs. O(n log n) time and O(1) extra space beyond the sort. Verified against brute force on 3,000 random inputs.

Coding 2 — backspace compare in O(1) space 
def backspace_compare(s: str, t: str) -> bool:
    """LeetCode 844 in O(1) space: walk both strings from the END,
    skipping characters erased by '#'."""
    def next_valid(x: str, k: int) -> int:
        skip = 0
        while k >= 0:
            if x[k] == '#':
                skip += 1
            elif skip:
                skip -= 1
            else:
                return k
            k -= 1
        return -1
    i, j = len(s) - 1, len(t) - 1
    while True:
        i, j = next_valid(s, i), next_valid(t, j)
        if i < 0 or j < 0:
            return i < 0 and j < 0
        if s[i] != t[j]:
            return False
        i -= 1; j -= 1

Walking backwards lets us know whether a character survives: we count pending #s and skip that many characters. Each index is visited once, so it is O(|s| + |t|) time and O(1) space. Verified against a stack-based simulation.

Coding 3 — boats to save people 
def num_rescue_boats(people: List[int], limit: int) -> int:
    """LeetCode 881: each boat holds at most 2 people and weight <= limit."""
    a = sorted(people)
    lo, hi = 0, len(a) - 1
    boats = 0
    while lo <= hi:                     # '<=': a single remaining person still needs a boat
        if a[lo] + a[hi] <= limit:
            lo += 1                     # lightest rides with heaviest
        hi -= 1                         # heaviest always leaves
        boats += 1
    return boats

Greedy and converging: the heaviest person always leaves on this boat. If the lightest person also fits, they ride together, because pairing the heaviest with anyone else could only leave a heavier person behind. Note lo <= hi: a single remaining person still needs a boat. O(n log n). Verified against an exhaustive optimum on small random inputs.

Engineering scenario — streaming merge with de-duplication

Design. Open both exports as line iterators, so only the current line of each is in memory. Keep one cursor per stream and repeatedly emit the smaller current ID, advancing that cursor. Skip an ID equal to the last one emitted, which removes duplicates both within and across streams, since equal IDs are adjacent in the merged order. This is the two-sequence merge of I.5 plus a "last written" check, the reader/writer idea applied to a stream.

def merge_unique(a: Iterable[int], b: Iterable[int]) -> Iterator[int]:
    """Engineering scenario: stream-merge two sorted inputs of any size,
    yielding each distinct value once. O(1) memory beyond two cursors."""
    ia, ib = iter(a), iter(b)
    sentinel = object()
    x, y = next(ia, sentinel), next(ib, sentinel)
    last = sentinel
    while x is not sentinel or y is not sentinel:
        if y is sentinel or (x is not sentinel and x <= y):
            v, x = x, next(ia, sentinel)
        else:
            v, y = y, next(ib, sentinel)
        if v != last:
            yield v
            last = v

Cost. Time Θ(N₁ + N₂) comparisons and O(1) memory (two current values plus the last emitted). The work is I/O-bound. Use buffered file reading and write output in chunks.

50 exports. Comparing 50 fronts each step costs O(k), so use a min-heap of the fronts: heapq.merge(*streams) gives O(N log k) time and O(k) memory [21]. Then de-duplicate with the same "skip if equal to last" filter, for example (k for k, _ in itertools.groupby(heapq.merge(*streams))). This is the same plan databases use for merge joins and external sorts [15].
