BFundamental understanding

What is complexity?

An algorithm consumes two scarce resources: time (how many steps the processor performs) and space (how much memory it occupies while running). Complexity analysis describes how those resource needs grow as a function of the input size n. MIT's 6.006 frames efficiency the same way: running time is measured by counting fixed-time operations, so the answer does not depend on a particular machine [2], and asymptotic ("big-O") notation describes the growth of the runtime without worrying about computers, compilers or implementations [3].

Formal definition The time complexity of an algorithm is a function T(n) giving the number of primitive operations it performs on an input of size n (usually in the worst case), under a fixed model of computation such as the word-RAM [2][1]. The space complexity S(n) is the maximum number of memory cells (words) in use at any moment during the run. Both are classified by their order of growth using asymptotic notation [4][5].
Plain-English definition Time complexity answers: "If I give this program twice as much data, how much longer will it take?" Space complexity answers: "…and how much more memory will it need?" We care about the shape of the growth (flat, straight line, parabola, explosion), not the exact number of milliseconds.

Why the concept exists

Timing a program with a stopwatch tells you about that program on that machine with that input. Princeton's Sedgewick and Wayne list the reasons we analyse algorithms instead: to predict performance, compare algorithms, provide guarantees and understand the theory — with the primary practical reason being to avoid performance bugs [6]. Their N-body example makes the point: a brute-force simulation needs about n² steps, which limited what scientists could simulate until faster algorithms arrived [6].

A short, verifiable history

The symbol O predates computers. Donald Knuth traced it to Paul Bachmann's 1894 number-theory book, after which Edmund Landau popularised it (and introduced little-o) [13]. In 1976 Knuth argued in SIGACT News that computer scientists also need notation for lower bounds and tight bounds, and proposed the now-standard Ω and Θ definitions [13]. Today these definitions are the ones taught in CLRS and in university courses [1][4].

CThe problem complexity analysis solves

Problem description

Input: two or more correct algorithms for the same task, plus an expected range of input sizes. Output: a prediction of how each will scale — and therefore which one to ship. Constraints: the prediction must be independent of hardware, language and compiler, and must hold as n grows beyond what we can test.

Why the naive approach (benchmarking only) falls short

Measuring wall-clock time is valuable — Princeton teaches an empirical "doubling" method in which you time the program at n and 2n and inspect the ratio [5] — but timing alone cannot tell you why a program is slow, cannot be done before the code exists, and cannot safely be extrapolated from small tests to 1000× larger production inputs. Wall-clock numbers also mix in effects of the machine, the interpreter and the cache that asymptotic analysis deliberately abstracts away [3].

How complexity analysis improves the situation

By counting the dominant operations as a function of n, we obtain a machine-independent "law" such as T(n) ∼ n³/6. Princeton shows this for the brute-force 3-SUM program, whose inner if executes exactly n(n−1)(n−2)/6 times, i.e. ∼ n³/6 [5]. A cubic law immediately predicts that doubling n multiplies running time by about 2³ = 8 — which is exactly what their measurements show [5].

Real-world analogy Illustration You must find a friend's name in a 1,000-page phone book. Reading every page in order is a linear strategy — 10× more pages means 10× more work. Opening the book in the middle, deciding which half the name is in, and repeating is a logarithmic strategy — 1,000 pages need about 10 halvings, and a million pages only about 20. Neither strategy depends on how fast you read; the difference is in the shape of the work. That shape is what complexity captures.

FInternal working: how cost is actually counted

The machine model underneath

To count "steps", we need to agree on what one step is. Courses such as MIT 6.006 use the word-RAM: memory is an array of w-bit words, and integer arithmetic, logical and bitwise operations, comparisons, and reading or writing a word at a given address each take O(1) time [2]. Because w ≥ log₂ n, an index into an array of n items fits in one word, which is exactly why a[i] is a constant-time operation [2].

The counting procedure

  1. Choose the input size n. For a list it is its length; for a graph, usually V and E; for a number, its number of bits.
  2. Choose the basic operation — the one in the innermost loop. Princeton's method focuses on the most frequently executed instructions, since time outside the inner loop is relatively insignificant [5].
  3. Write the count as a sum (loops) or a recurrence (recursion).
  4. Simplify to a closed form, e.g. ∑ᵢ₌₀ⁿ⁻¹ (n−1−i) = n(n−1)/2.
  5. Keep the leading term, drop its constant: n(n−1)/2 ∼ n²/2 ⟹ Θ(n²) [5][1].

Memory representation: where does space go?

A running program's memory splits into the input (given to us), auxiliary data (variables, new lists, hash tables we build), and the call stack (one frame per active function call). Space complexity usually means the auxiliary part plus the stack. In CPython a list is internally an array of references to objects [10], and the interpreter limits recursion depth with a configurable limit that exists to prevent infinite recursion from overflowing the C stack and crashing Python [11].

Edge cases that change the answer

  • Empty input (n = 0). Most loops run zero times, but a function like find_max([]) must decide whether to raise an error — complexity doesn't excuse incorrect behaviour.
  • Early exit. Linear search that finds the target at index 0 costs 1 comparison (best case), but its worst case is still n.
  • Hidden copies. Slicing, list(x), sorted(x), string building and a + b all allocate new storage proportional to their output [9].
  • Input size in bits. For numeric inputs, the size is the number of digits, not the value (see Section N).

GMathematical foundation

The three core definitions

Let f, g be functions from non-negative integers to non-negative reals. The definitions below are those of CLRS and Stanford CS161 [1][4]:

Big-O — an upper bound f(n) = O(g(n)) ⟺ there exist constants c > 0 and n₀ such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀.
Big-Omega — a lower bound f(n) = Ω(g(n)) ⟺ there exist c > 0 and n₀ such that 0 ≤ c·g(n) ≤ f(n) for all n ≥ n₀.
Big-Theta — a tight bound f(n) = Θ(g(n)) ⟺ f(n) = O(g(n)) and f(n) = Ω(g(n)); equivalently there exist c₁, c₂ > 0 and n₀ with c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀.

MIT's Mathematics for Computer Science text stresses that Big-O gives an upper bound on growth and is the most frequently used asymptotic notation [14]. The "=" sign is a long-standing abuse of notation: O(g) is really a set of functions, and MIT's 6.006 recitation notes call f(x) = Θ(x²) "really misleading" for that reason [3].

Worked proofs

Claim 1. 3n² + 5n + 2 = O(n²). Proof. For n ≥ 1 we have 5n ≤ 5n² and 2 ≤ 2n², so 3n² + 5n + 2 ≤ 10n². Choose c = 10, n₀ = 1. ∎ (Many witnesses work: c = 4 with n₀ = 6 also works, because n² − 5n − 2 ≥ 0 once n ≥ 5.37.)

Claim 2. 3n² + 5n + 2 = Ω(n²). Proof. For n ≥ 0, 3n² + 5n + 2 ≥ 3n². Choose c = 3, n₀ = 0. ∎ Together, Claims 1 and 2 give Θ(n²).

Claim 3. n² ≠ O(n). Proof by contradiction. Suppose n² ≤ c·n for all n ≥ n₀. Dividing by n gives n ≤ c for all n ≥ n₀, which fails at n = max(n₀, ⌈c⌉ + 1). ∎

The limit test (a shortcut) If L = limn→∞ f(n)/g(n) exists, then L = 0 ⟹ f = o(g) (hence O(g)); 0 < L < ∞ ⟹ f = Θ(g); L = ∞ ⟹ f = ω(g) (hence Ω(g)) [16]. Little-o and little-ω are the strict versions of O and Ω: f = o(g) means f grows strictly slower [16][13].

HOperations and complexity analysis

Best, average, worst — and why worst case is the default

Stanford CS161 frames worst-case analysis as a game against an adversary who picks the input: a worst-case guarantee holds for every input of size n, which makes it a strong and robust promise [4]. Average-case analysis needs an assumed input distribution (e.g. "every permutation equally likely") [1]. Best case is rarely useful on its own, since almost any algorithm can be made fast on some lucky input.

Common confusionBig-O ≠ worst case and Ω ≠ best case. O, Ω and Θ are bounds on functions; best/worst/average choose which function you are bounding. "Insertion sort's best case is Θ(n) and its worst case is Θ(n²)" uses Θ for both [1].

Amortized analysis: why append is O(1) although resizing is O(n)

Amortized cost = total cost of a sequence of k operations ÷ k [7]. It is a worst-case guarantee about sequences, not an average over random inputs. MIT 6.046 presents three techniques — the aggregate, accounting and potential methods — and applies them to table doubling [7][18].

Aggregate method. Start with capacity 1 and double when full. Inserting n items triggers copies of 1 + 2 + 4 + … + 2⌊log₂(n−1)⌋ < 2n elements (geometric series), plus n writes, so the total is < 3n and each append costs O(1) amortized [7].

Accounting method. Charge every insert 3 coins: one pays for the write, two are saved. When the table of size m doubles, the m/2 items inserted since the last doubling have saved m coins — exactly enough to move all m items [7].

CPython's actual policy is not exact doubling: the list implementation over-allocates proportionally to the list size, "mild" but enough for linear-time amortized behaviour over a long sequence of appends [19][9]. Any growth by a constant factor gives amortized O(1); growth by a constant amount (e.g. +10 slots) gives Θ(n²) total.

Time–space trade-offs

Many speed-ups buy time with memory. The duplicate check is the textbook case: the all-pairs version uses Θ(n²) time and Θ(1) space, while the hash-set version uses O(n) average time and O(n) space (Section I). Memoization (Lab 4) stores Θ(n) results to turn exponential time into linear time. Prefix sums store n + 1 numbers so that any range sum takes O(1). The reverse trade also exists: the iterative Fibonacci keeps only two variables, Θ(1) space, by recomputing rather than storing.

I.1 The instrumentation idea

Instead of a stopwatch, each function receives an OpCounter and calls c.tick() once per basic operation (the comparison in the innermost loop). This is the "count the inner loop" method from Princeton [5] turned into code.

class OpCounter:
    """Counts 'basic operations' so we can see growth without a stopwatch."""
    def __init__(self):
        self.ops = 0
    def tick(self, k=1):
        self.ops += k

I.2 One function per complexity class

def get_first(a, c):                 # Θ(1): one index, independent of n
    c.tick()
    return a[0] if a else None

def binary_search(a, target, c):     # O(log n): interval halves each pass
    lo, hi = 0, len(a) - 1                 # invariant: target, if present, is in a[lo..hi]
    while lo <= hi:
        c.tick()
        mid = (lo + hi) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1                    # discard left half
        else:
            hi = mid - 1                    # discard right half
    return -1

def has_duplicate_quadratic(a, c):   # O(n²) time, O(1) extra space
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):         # triangular loop: n(n-1)/2 pairs
            c.tick()
            if a[i] == a[j]:
                return True
    return False

def has_duplicate_set(a, c):         # O(n) average time, O(n) extra space
    seen = set()
    for x in a:
        c.tick()
        if x in seen:                    # O(1) average membership test
            return True
        seen.add(x)
    return False

Line notes. In binary_search, the loop invariant "if the target is present it lies in a[lo..hi]" is what makes discarding half the array safe; each iteration shrinks hi − lo + 1 to at most half, so there are at most ⌊log₂ n⌋ + 1 iterations [1]. (lo + hi) // 2 cannot overflow in Python because integers have unbounded precision; in fixed-width languages write lo + (hi − lo) // 2. In has_duplicate_set, x in seen and seen.add(x) are O(1) on average and O(n) in the worst case [9].

I.3 Space: recursion versus iteration, and exponential versus linear

def sum_recursive(a, i=0):           # O(n) time, O(n) call-stack space
    if i == len(a):                     # base case
        return 0
    return a[i] + sum_recursive(a, i + 1)

def sum_iterative(a):                # O(n) time, O(1) auxiliary space
    total = 0
    for x in a:
        total += x
    return total

def fib_naive(n, c):                 # Θ(φⁿ) time, Θ(n) stack
    c.tick()
    if n < 2:
        return n
    return fib_naive(n - 1, c) + fib_naive(n - 2, c)

def fib_iter(n):                     # Θ(n) time, Θ(1) auxiliary space
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

I.4 A dynamic array from scratch, with amortized accounting

class DynamicArray:
    """Doubling array: append is O(1) amortized, O(n) worst case."""
    def __init__(self):
        self._cap, self._n = 1, 0
        self._data = [None] * self._cap
        self.copies = 0                   # element moves caused by resizing
    def __len__(self):
        return self._n
    def __getitem__(self, i):
        if not 0 <= i < self._n:           # error handling: reject out-of-range
            raise IndexError("DynamicArray index out of range")
        return self._data[i]
    def append(self, x):
        if self._n == self._cap:         # full → grow by a constant FACTOR
            self._resize(2 * self._cap)
        self._data[self._n] = x
        self._n += 1
    def _resize(self, new_cap):         # Θ(n): copy every element
        new = [None] * new_cap
        for k in range(self._n):
            new[k] = self._data[k]
            self.copies += 1
        self._data, self._cap = new, new_cap

I.5 Measuring instead of guessing

The standard library provides time.perf_counter/timeit for timing [17] and tracemalloc for tracing memory allocations, including the peak size of traced blocks [20]. The doubling experiment reproduces Princeton's method: if T(n) ∼ c·nb, then T(2n)/T(n) → 2b [5].

def peak_bytes(fn, *args):

I.8 Edge cases and error handling

import sys, time, tracemalloc
from functools import lru_cache

# ---------- 1. Instrumented step counter ----------
class OpCounter:
    """Counts &#x27;basic operations' so we can see growth without a stopwatch."""
    def __init__(self):
        self.ops = 0
    def tick(self, k=1):
        self.ops += k

def get_first(a, c):                 # O(1)
    c.tick()
    return a[0] if a else None

def find_max(a, c):                  # Θ(n)
    if not a:
        raise ValueError("find_max() of empty sequence")
    best = a[0]
    for x in a[1:]:
        c.tick()                     # one comparison per remaining element
        if x > best:
            best = x
    return best

def binary_search(a, target, c):     # O(log n)
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        c.tick()
        mid = (lo + hi) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

def merge_sort(a, c):                # Θ(n log n) time, Θ(n) aux space
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left, right = merge_sort(a[:mid], c), merge_sort(a[mid:], c)
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        c.tick()
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

def has_duplicate_quadratic(a, c):   # O(n^2) time, O(1) aux space
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):
            c.tick()
            if a[i] == a[j]:
                return True
    return False

def has_duplicate_set(a, c):         # O(n) average time, O(n) aux space
    seen = set()
    for x in a:
        c.tick()
        if x in seen:
            return True
        seen.add(x)
    return False

# ---------- 2. Exponential vs linear: Fibonacci ----------
def fib_naive(n, c):                 # Θ(φ^n) time, Θ(n) stack space
    c.tick()
    if n < 2:
        return n
    return fib_naive(n - 1, c) + fib_naive(n - 2, c)

def fib_memo(n, c, memo=None):       # Θ(n) time, Θ(n) space
    if memo is None:
        memo = {}
    c.tick()
    if n < 2:
        return n
    if n in memo:
        return memo[n]
    memo[n] = fib_memo(n - 1, c, memo) + fib_memo(n - 2, c, memo)
    return memo[n]

def fib_iter(n):                     # Θ(n) time, Θ(1) aux space
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

# ---------- 3. Space: recursion stack vs loop ----------
def sum_recursive(a, i=0):           # O(n) call-stack space
    if i == len(a):
        return 0
    return a[i] + sum_recursive(a, i + 1)

def sum_iterative(a):                # O(1) auxiliary space
    total = 0
    for x in a:
        total += x
    return total

# ---------- 4. Dynamic array with amortized-cost accounting ----------
class DynamicArray:
    """Doubling array: append is O(1) amortized, O(n) worst case."""
    def __init__(self):
        self._cap, self._n = 1, 0
        self._data = [None] * self._cap
        self.copies = 0              # element moves caused by resizing
    def __len__(self):
        return self._n
    def __getitem__(self, i):
        if not 0 <= i < self._n:
            raise IndexError("DynamicArray index out of range")
        return self._data[i]
    def append(self, x):
        if self._n == self._cap:
            self._resize(2 * self._cap)
        self._data[self._n] = x
        self._n += 1
    def _resize(self, new_cap):
        new = [None] * new_cap
        for k in range(self._n):
            new[k] = self._data[k]
            self.copies += 1
        self._data, self._cap = new, new_cap

JReal-world applications

Complexity is not an exam topic that disappears after graduation; it is how engineers reason about whether a system will survive growth. Princeton's course names the primary practical reason for analysis bluntly: avoiding performance bugs, where a client gets poor performance because a programmer did not understand performance characteristics [6].

DomainWhere complexity decides the outcome
Backend engineeringIllustration A request handler that checks each of n incoming IDs with id in allowed_list is O(n·m); converting allowed_list to a set makes it O(n + m) on average [9]. The "N + 1 queries" anti-pattern (one query per row instead of one batched query) is the same mistake at the network level: cost grows linearly in round trips.
DatabasesIndexed lookups follow a balanced tree (O(log n)) instead of scanning (O(n)) — Figure J.1 [1]. Sorting-based operations such as ORDER BY or merge joins inherit the Ω(n log n) comparison-sorting lower bound unless an index already provides order [1].
Operating systems & runtimesCall stacks are finite. CPython's recursion limit exists to stop runaway recursion from overflowing the C stack and crashing the interpreter [11], so an algorithm's O(depth) stack space is an operational constraint, not just a theoretical one.
Networking & securityHash tables are O(1) only on average; when every key collides, operations become O(n) [9]. Attackers exploited this against web frameworks with crafted keys; Python responded by adding PYTHONHASHSEED hash randomization to protect against denial-of-service from worst-case dict behaviour [21].
Distributed systemsIllustration Any "every node talks to every node" protocol sends Θ(n²) messages per round; at 10 nodes that is 90 messages, at 1,000 nodes nearly a million — which is why large clusters prefer designs whose per-round cost is linear or logarithmic in cluster size.
Search enginesIllustration Search is dominated by sorted structures: binary search and merging of sorted lists are O(log n) and O(n + m) respectively [1], which is what makes querying web-scale collections feasible without scanning every document.
Web applicationsFront-end lists that re-filter all n items on every keystroke are O(n) per keystroke; adding a nested lookup inside the filter silently makes it O(n²). Profiling plus complexity reasoning finds these quickly.
Large-scale softwareCapacity planning uses the doubling hypothesis: measure at n and 2n, infer the exponent from the ratio, and predict cost at 10n before it ships [5][6].

L.1 Hidden linear work inside a loop

✗ Looks O(n), is O(n·m) 
result = []
for x in items:            # n times
    if x in banned_list:   # O(m) scan!
        result.append(x)
✓ O(n + m) average 
banned = set(banned_list)    # O(m) once
result = [x for x in items
          if x in banned]      # O(1) avg

x in list is O(n), x in set is O(1) on average [9].

L.2 Using a list as a queue

✗ O(n) per dequeue 
queue = [start]
while queue:
    node = queue.pop(0)  # shifts all
✓ O(1) per dequeue 
from collections import deque
queue = deque([start])
while queue:
    node = queue.popleft()

list.pop(k) costs O(n − k), so pop(0) is O(n) [9]; deque.popleft() is O(1) [12]. Over a BFS of n nodes this is the difference between O(n²) and O(n).

L.3 Slicing in recursion

✗ "Binary search" that is O(n) 
def bs(a, t):
    if not a: return False
    m = len(a) // 2
    if a[m] == t: return True
    return bs(a[m+1:], t) if a[m] < t \
        else bs(a[:m], t)   # copies!
✓ O(log n): pass indices 
def bs(a, t, lo=0, hi=None):
    hi = len(a) - 1 if hi is None else hi
    if lo > hi: return False
    m = (lo + hi) // 2
    if a[m] == t: return True
    return bs(a, t, m+1, hi) if a[m] < t \
        else bs(a, t, lo, m-1)

A slice a[i:j] costs O(j − i) [9], so the left version copies n/2 + n/4 + … ≈ n elements: Θ(n) time and Θ(n) extra memory, despite doing only O(log n) comparisons.

L.4 Complexity misconceptions

MisconceptionCorrection
"Big-O means worst case."O is an upper bound on a function; worst/best/average choose the function. You can give an O bound on the best case [1].
"O(n) means exactly proportional to n."O is only an upper bound; 3n + 4 is O(n²) too. Use Θ when you mean "exactly this order". NIST's dictionary notes Big-O is often misused to mean "equal to" [15].
"Two nested loops ⇒ O(n²)."Only if both run Θ(n) times. An inner halving loop gives O(n log n); a two-pointer inner loop whose pointer never resets gives O(n) total.
"O(n/2) is better than O(n)."Constants are dropped: O(n/2) = O(n) [4].
"Dict lookups are always O(1)."Average O(1); worst case O(n) when keys collide [9].
"Recursion uses no extra memory."Each active call holds a stack frame: depth d ⇒ Θ(d) space (Figure F.1).
"Amortized O(1) means every call is fast."Individual appends can be O(n); only the sequence average is bounded [9][7].
"With two inputs, write O(n)."Keep both variables: merging lists of sizes n and m is O(n + m); a grid is O(rows·cols).

L.5 Boundary-condition and interview mistakes

  • Forgetting output size. Generating all subsets of n items must write 2ⁿ subsets of average length n/2, so it is Ω(n·2ⁿ) no matter how clever the code.
  • Not defining n. In an interview, say "let n be the length of the string and k the alphabet size" before giving a bound.
  • Ignoring space. Always state both: "O(n) time, O(1) extra space excluding the output."
  • Off-by-one in logs. Binary search does at most ⌊log₂ n⌋ + 1 comparisons, not log₂ n (Lab 3 shows both).
  • Measuring a cold run once. Repeat timings and compare ratios, as timeit encourages [17].

NAdvanced concepts

N.1 The potential method

The most general amortization technique assigns a potential Φ to the data structure's state and defines amortized cost = actual cost + Φ(after) − Φ(before); summing telescopes to actual total + Φ(final) − Φ(initial), so any Φ that starts at 0 and stays non-negative yields valid bounds [7][18]. For a doubling table, Φ = 2·size − capacity works: cheap inserts raise Φ by 2, and a resize's Θ(n) copying is paid for by the drop in Φ.

N.2 Expected time of randomized algorithms

Randomized quicksort runs in expected O(n log n) on every input, because the randomness lives in the algorithm, not the data; its worst case remains Θ(n²) [1]. This differs from average-case analysis, which assumes a distribution over inputs.

N.3 Lower bounds: proving you can't do better

Any comparison-based sorting algorithm needs Ω(n log n) comparisons in the worst case, by the decision-tree argument: there are n! possible orderings, a binary decision tree with n! leaves has height ≥ log₂(n!) = Θ(n log n) [1]. So merge sort is asymptotically optimal among comparison sorts; beating n log n requires extra assumptions (e.g. integer keys for counting or radix sort) [1].

N.4 Input size in bits and pseudo-polynomial time

Complexity is measured in the size of the input. A loop for d in range(2, N) that tests whether N is prime is O(N) — linear in the value, but the input is only b ≈ log₂ N bits long, so it is O(2b): exponential in the input size. Algorithms polynomial in a numeric value but not in its bit length are called pseudo-polynomial (the classic 0/1-knapsack DP is O(n·W)). MIT 6.006 defines efficiency as polynomial time with respect to the input size [2].

N.5 Multi-parameter and output-sensitive bounds

Graph algorithms are stated in V and E (BFS/DFS: O(V + E)) [1]; string matching in text length and pattern length; and output-sensitive algorithms include the output size k, e.g. reporting all k points in a range. Collapsing these into one "n" loses information.

N.6 Beyond the RAM model

The word-RAM charges every memory access the same O(1) [2], but real hardware has caches and disks where locality dominates. External-memory models count block transfers instead — another reason B-trees use wide nodes. MIT's performance-engineering course (6.172) builds on the same divide-and-conquer recurrences used here [8].

P.5 Answer key

Conceptual answers
  1. Yes: n² ≤ 1·n³ for n ≥ 1 (c = 1, n₀ = 1). No: Θ would need n² ≥ c·n³, i.e. n ≤ 1/c for all large n — impossible. So n² = O(n³) but n² = o(n³), not Θ.
  2. log₂ n = log₁₀ n / log₁₀ 2, a constant factor, which O absorbs. But 3ⁿ / 2ⁿ = (1.5)ⁿ → ∞, so no constant c makes 3ⁿ ≤ c·2ⁿ: different classes.
  3. list.append: a single call that triggers a resize copies all n elements (O(n)), but over any sequence of k appends the total is O(k) [9][7]. Worst-case bounds a single operation; amortized bounds the average over a sequence — both are true.
  4. Time counts all nodes of the recursion tree (up to 2ⁿ). Space counts only frames alive simultaneously — a single root-to-leaf path of length n — because a call's frame is freed when it returns (Lab 4).

Coding answers 
import math, random, time
from collections import deque

# 1. Pair with difference k
def has_pair_diff_slow(nums, k):        # Θ(n²) time, Θ(1) space
    n = len(nums)
    return any(abs(nums[i] - nums[j]) == k
               for i in range(n) for j in range(i + 1, n))

def has_pair_diff_fast(nums, k):        # O(n) average time, O(n) space
    s = set(nums)
    return any(x + k in s for x in nums)

# 2. Level order with a deque: O(n) time, O(width) queue space
def levels(root):
    if root is None:
        return []
    q, out = deque([root]), []
    while q:
        node = q.popleft()
        out.append(node.val)
        q.extend(c for c in (node.left, node.right) if c)
    return out

# 3. Empirical exponent via the doubling hypothesis
def estimate_exponent(fn, n, repeats=5):
    def best_time(size):
        data = [random.random() for _ in range(size)]
        best = float("inf")
        for _ in range(repeats):
            t0 = time.perf_counter(); fn(data); best = min(best, time.perf_counter() - t0)
        return best
    return math.log2(best_time(2 * n) / best_time(n))

def all_pairs(a):
    c = 0
    for i in range(len(a)):
        for j in range(i + 1, len(a)):
            c += 1
    return c

Engineering scenario — model answer

Diagnose. All-pairs comparison is Θ(n²) (n(n−1)/2 pairs × 50 fields). Going from 2,000 to 40,000 customers multiplies n by 20, so time grows by ≈ 20² = 400: 0.4 s × 400 ≈ 160 s per request. With 10% monthly growth, n doubles roughly every 7.3 months, quadrupling the time each doubling [5].

Hardware. A 4× faster server buys exactly one doubling of n — about 7 months — after which the problem returns. Faster machines change the constant, not the class.

Redesign. (1) Answer per-customer queries instead of recomputing all pairs: compare one customer against n others, O(n) per request. (2) Precompute offline in batch jobs, cache results, and refresh incrementally. (3) Index by blocking keys (region, segment) or use approximate nearest-neighbour indexing so each query inspects a small candidate set rather than all n. (4) Measure with a doubling experiment after each change to confirm the new exponent.
