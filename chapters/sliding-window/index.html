BFundamental understanding

What is a sliding window?

Many questions about arrays and strings ask about contiguous pieces: "the best 7-day stretch of sales", "the longest substring with no repeated letter", "the maximum in every 3-element block". A window is such a contiguous piece, described by two indices: a left end L and a right end R. The Competitive Programmer's Handbook defines a sliding window as "a constant-size subarray that moves from left to right through the array", for each position of which we compute some information [1][2]. The USACO Guide describes the variable-size form as a variation of the two pointers method in which both pointers move in the same direction to maintain a range of elements [3].

Formal definition Let a[0..n−1] be a sequence. A window is an index interval [L, R] with 0 ≤ L ≤ R < n, denoting the contiguous subsequence a[L], a[L+1], …, a[R] of length R − L + 1. A sliding-window algorithm visits a sequence of windows [L₀,R₀], [L₁,R₁], … in which both endpoints are non-decreasing (Lt+1 ≥ Lt, Rt+1 ≥ Rt), and maintains a summary state(L, R) that is updated incrementally when an element enters at the right or leaves at the left.
• Fixed-size window: R − L + 1 = k for every visited window, so each move adds one element and removes one [1].
• Variable-size window: the length changes; R advances to grow the window and L advances to shrink it, as long as both only move right [2][3].
In plain English Put a paper frame over a row of numbers. To look at the next group, you don't rewrite everything inside the frame — you slide it one place, cross off the number that fell out on the left, and add the one that appeared on the right.

Why the concept exists

The brute-force way to examine every window recomputes its summary from nothing. For fixed size k that costs about k operations per window and (n − k + 1)·k in total; for "find the best window of any length" there are n(n+1)/2 windows, so brute force is Θ(n²) windows, and Θ(n³) if each is re-summed. But consecutive windows share almost everything: [L, R] and [L+1, R+1] share k − 1 elements. A sliding window exploits that overlap. The Handbook presents the two-pointers method and the sliding-window minimum in its chapter on amortized analysis precisely because the work of a single step can vary while the total stays linear [1].

A short, verifiable history

"Sliding window" is a family name more than a single invention, and the idea appears in several fields:

  • Networking (1981 onward). TCP controls how much unacknowledged data may be in flight using a send window over the sequence-number space; the current specification, RFC 9293 (2022), which obsoletes the original RFC 793 from 1981, defines the send variables SND.UNA, SND.NXT and SND.WND and calls part of the sequence space "the send window" [13].
  • String matching (1987). Karp and Rabin's randomized pattern-matching algorithm computes a fingerprint of each length-m window of the text and updates it in constant time as the window moves — a rolling hash [8][6][5].
  • Image processing (1992). van Herk published a running max/min filter whose cost per pixel does not depend on the window size [19].
  • Data streams (2002). Datar, Gionis, Indyk and Motwani formalised the sliding window model of streaming — answer queries about only the last N items — and showed how to approximate counts and sums in small memory [17][18].
  • Algorithm education and competitive programming. The fixed window, the two-pointer variable window and the deque-based window minimum are standard material in the Competitive Programmer's Handbook, the USACO Guide and CP-Algorithms [1][2][4].

Three principles carry the whole chapter. (1) Reuse: derive state(L′, R′) from state(L, R) rather than from scratch. (2) Monotone pointers: neither pointer moves backward, so the number of moves is at most 2n — this is the amortized argument behind the two-pointers method [1]. (3) Cheap updates: entering and leaving must each cost O(1), at least on average. That is easy for sums, and needs a cleverer structure — a monotonic deque or two stacks — for minima and maxima, which cannot be "subtracted" [4].

CThe problem statement

Problem description

We study two canonical problems, one of each kind.

Problem 1 · fixed window Input: an integer array a of length n and an integer k, 1 ≤ k ≤ n.
Output: the largest sum of any k consecutive elements.
Example: a = [2,1,5,1,3,2], k = 3 → 9 (window [5,1,3]).
Typical constraints: n ≤ 10⁵ … 10⁶, values may be negative.
Problem 2 · variable window Input: a string s of length n.
Output: the length of the longest substring with no repeated character.
Example: "abcabcbb" → 3 ("abc"); "pwwkew" → 3 ("wke").
Typical constraints: n ≤ 5·10⁴, any characters. This is LeetCode 3 [22].

Why the naive approach is inefficient

For Problem 1, summing each of the n − k + 1 windows separately costs (n − k + 1)·k additions. With n = 10⁶ and k = 10³ that is about 10⁹ — seconds to minutes in Python — while the sliding version needs about k + 2(n − k) ≈ 2·10⁶ operations (Figure D.4). For Problem 2, checking every substring for uniqueness examines Θ(n²) substrings at Θ(n) each, Θ(n³) total; even the smarter "extend each start until a repeat" is Θ(n²) in the worst case. The sliding window solves both in Θ(n) [1][2].

Limitations of alternative approaches

  • Prefix sums answer any range-sum query in O(1) after O(n) preprocessing, so they solve Problem 1 too — but they need O(n) extra memory and only work for invertible aggregates like sums. They cannot give a window's maximum, its number of distinct letters or "is it an anagram?" by subtraction (see Chapter 03).
  • A heap can keep a window maximum in O(log k) per step, so O(n log k) overall, and needs "lazy deletion" because heaps cannot remove arbitrary elements cheaply. A monotonic deque does the same job in amortized O(1) per step [4][2].
  • Segment trees and sparse tables answer arbitrary range queries, which is more than we need when the queried ranges move in one direction.

How the sliding window improves the solution

Both problems have the same hidden structure: the windows we care about can be visited in an order in which both endpoints only move right, and the summary can be updated in O(1) when one element enters or leaves. Under those two conditions the total work is proportional to the number of pointer moves, which is at most 2n [1].

Real-world analogy: the train window Illustration You are on a train counting houses visible through your window. When the train moves forward by one house, you don't recount the whole view — one house disappeared at the back edge and one appeared at the front. Keep a running tally, subtract the one that left, add the one that arrived. A variable window is like a caterpillar crawling along a branch: its head (R) reaches forward; when it is stretched too far (the window became invalid) its tail (L) catches up; neither end ever crawls backwards.

FInternal working

Memory representation: what the algorithm actually stores

A sliding window never copies the window. It stores the input once (which it reads but does not change), two integers L and R, and a window state sized to the question. Slicing a[L:R+1] inside the loop would silently bring the brute-force cost back, because a Python slice copies its elements, which is O(k) [11].

The three operations every window needs

  1. add(a[R]) — fold the entering element into the state (s += x, count[x] += 1, push onto the deque).
  2. remove(a[L]) — undo the leaving element (s -= x, count[x] -= 1 and delete the key at zero, pop the deque front if it has expired).
  3. query() — read the answer for the current window (s, len(count), a[dq[0]]).

Once these three are O(1), every window problem reduces to choosing when to call them.

Execution flow: the four templates

Template 1 · fixed size k 
for R in range(n):
    add(a[R])                 # enters
    if R >= k:
        remove(a[R - k])      # leaves
    if R >= k - 1:
        record(query())       # window full
Template 2 · longest valid 
L = 0
for R in range(n):
    add(a[R])
    while invalid():         # repair
        remove(a[L]); L += 1
    best = max(best, R - L + 1)
Template 3 · shortest valid 
L = 0
for R in range(n):
    add(a[R])
    while valid():           # tighten
        best = min(best, R - L + 1)
        remove(a[L]); L += 1
Template 4 · count valid 
L = total = 0
for R in range(n):
    add(a[R])
    while invalid():
        remove(a[L]); L += 1
    total += R - L + 1        # all starts L..R

The difference between Templates 2 and 3 is where the answer is recorded. For "longest" we repair the window until it is valid, then record. For "shortest" we record while the window is valid, shrinking it after each record. Template 4 relies on the same monotonicity: if [L, R] is the widest valid window ending at R, then every [L′, R] with L ≤ L′ ≤ R is valid too, giving R − L + 1 valid subarrays ending at R [1][3].

State changes, numbered: longest substring without repeats

For Problem 2 the state is a dictionary last_seen[ch] holding the most recent index of each character. When s[R] was already seen inside the window, L can jump straight past the earlier copy instead of shrinking one step at a time:

  1. Read ch = s[R].
  2. If ch in last_seen and last_seen[ch] ≥ L, the window would contain ch twice: set L = last_seen[ch] + 1.
  3. Record last_seen[ch] = R.
  4. The window [L, R] now has no repeats: update best = max(best, R − L + 1).

The monotonic deque, internally

For window maxima the state is a double-ended queue of indices whose values are strictly decreasing from front to back. CP-Algorithms describes the min-version: keep only the elements that can still become the minimum, in non-decreasing order, and before pushing a new value pop every larger value from the back [4]. The USACO Guide uses a decreasing deque for the maximum and stores indices so it can tell when the front has left the window [2]. On each step R:

  1. Pop dominated from the back: while a[dq[-1]] ≤ a[R], pop. Those elements are older and not larger than a[R], so they can never again be the maximum of a window that contains R.
  2. Push R onto the back.
  3. Expire from the front: if dq[0] ≤ R − k, that index has left the window — pop it from the front.
  4. Query: once R ≥ k − 1, the window maximum is a[dq[0]].

Python's collections.deque supports appends and pops at either end in approximately O(1) time, whereas a list costs O(n) for pop(0) and insert(0, v) [9]. That is why a list is the wrong container here.

GMathematical foundation

G.1 The fixed-window update identity

Let S(i) = Σj=ii+k−1 a[j] be the sum of the window starting at i. Then

S(i+1) = Σj=i+1i+k a[j] = ( Σj=ii+k−1 a[j] ) − a[i] + a[i+k] = S(i) − a[i] + a[i+k].

Proof. The two sums share the terms a[i+1], …, a[i+k−1]; the first also has a[i] and the second also has a[i+k]. Adding and subtracting those single terms converts one into the other. ∎ The proof uses only associativity, commutativity and an inverse, so the identity holds for any abelian group operation — sum, xor, or multiplication over non-zero numbers. Max, min and gcd have no inverse, which is why they need a different structure [4].

G.2 Monotone validity: why L never has to move back

Call a condition P on windows shrink-closed if P([L, R]) implies P([L′, R′]) whenever L ≤ L′ ≤ R′ ≤ R: every sub-window of a valid window is valid. "At most K distinct values", "no repeated character" and "sum ≤ T with non-negative numbers" are shrink-closed. Define, for each R, the smallest valid left end L*(R) = min{ L : P([L, R]) }.

Lemma (monotone left end) If P is shrink-closed then L*(R) ≤ L*(R+1).

Proof. Let L′ = L*(R+1), so [L′, R+1] is valid. If L′ ≤ R, its sub-window [L′, R] is valid by shrink-closure, so L*(R) ≤ L′. If L′ = R+1, the inequality L*(R) ≤ R < L′ holds because the single-element window [R, R] is valid in these problems. ∎

Correctness of Template 2. Invariant: at the end of iteration R, L = L*(R). By the lemma, the correct left end for R+1 is never to the left of the current L, so starting from the current L and advancing while the window is invalid lands exactly on L*(R+1). Each window [L*(R), R] is the longest valid window ending at R, and the overall longest valid window ends at some R, so taking the maximum over R is correct. Template 4 counts, for each R, the valid windows [L′, R] with L*(R) ≤ L′ ≤ R; by shrink-closure that is all of them, R − L*(R) + 1.

For "shortest with sum ≥ target" (Template 3) the condition is grow-closed instead — every super-window of a valid window is valid when all numbers are positive — and the symmetric argument shows that the largest valid left end is also non-decreasing in R.

G.3 The 2n bound (aggregate amortized analysis)

In any two-pointer window, R takes the values 0, 1, …, n−1 once each, and L only increases and never exceeds n, so the inner while loop runs at most n times in total across the whole execution, even though a single iteration may shrink many times. The total number of add + remove calls is therefore at most n + n = 2n. This is the aggregate method of amortized analysis: bound the total cost of a sequence of operations, then divide [5][1].

G.4 The monotonic deque invariant

Invariant (maximum version) After processing index R, the deque holds indices i₁ < i₂ < … < im = R, all inside the window, with a[i₁] > a[i₂] > … > a[im], and a[i₁] = max a[R−k+1..R].

Why the front is the maximum. Suppose an index j in the window was removed from the back. It was removed when some later index j′ > j with a[j′] ≥ a[j] arrived. Because j′ > j, j′ stays in every window that still contains j, so j can never be the unique maximum: it is dominated. Every index that is not dominated is still in the deque, and the decreasing order makes the front the largest of them. Cost. Each index is pushed exactly once and popped at most once, from the back or the front, so the total number of deque operations is at most 2n, which is amortized O(1) per element and O(n) overall [4][1].

G.5 Counting identities: "exactly K" from "at most K"

"Exactly K distinct" is not shrink-closed: removing an element can drop the count to K − 1. But "at most K" is, and

#{windows with exactly K distinct} = #{≤ K} − #{≤ K−1},

because the windows with at most K distinct values split into those with exactly K and those with at most K − 1. Each right-hand term is one run of Template 4, so the whole computation is Θ(n). On [1,2,1,2,3] with K = 2: atMost(2) = 12, atMost(1) = 5, difference 7 (verified in Section I). This is the standard solution to LeetCode 992 [22].

G.6 Rolling hashes (the same identity, modulo a prime)

Rabin–Karp treats a length-m window as a base-B number modulo a prime q: h(i) = (a[i]·Bm−1 + … + a[i+m−1]) mod q. Sliding by one gives

h(i+1) = ( (h(i) − a[i]·Bm−1)·B + a[i+m] ) mod q,

which is G.1 in a different group. The update is O(1), so all window hashes cost O(n + m), and equal hashes are confirmed by a direct comparison when needed [6][7][8].

Reasoning behind each entry

  • Fixed window, Θ(n) in all cases. The first window costs k − 1 additions and each of the n − k slides costs one subtraction and one addition: exactly (k−1) + 2(n−k) arithmetic operations, between n−1 and 2n. It is O(n) because it is at most 2n, Ω(n) because every element must be read at least once, hence Θ(n).
  • Variable window, Θ(n). The 2n bound of G.3 gives O(n); reading every element gives Ω(n). One outer iteration can be Θ(n) on its own, which is the reason the bound is stated as amortized [1][5].
  • Monotonic deque, Θ(n). At most n pushes and n pops in total (G.4) [4].
  • Heap. Each push or pop costs O(log size), and with lazy deletion the heap can hold up to n entries, so O(n log n).

Time–space trade-offs

A fixed-window sum uses O(1) space; prefix sums use O(n) space but answer arbitrary ranges, not just sliding ones. A monotonic deque uses up to O(k) memory to make max/min O(1) amortized; the alternative O(1)-space approach re-scans each window for Θ(n·k) time. In streaming systems where the window itself is too large to keep, exact answers can require memory proportional to the window, which motivates the approximate sketches in Section N [17].

I.1 Fixed window: maximum sum of k consecutive elements

def _check_k(n: int, k: int) -> None:
    if not isinstance(k, int) or isinstance(k, bool):
        raise TypeError("k must be an int")
    if k <= 0:
        raise ValueError("k must be positive")
    if k > n:
        raise ValueError(f"k={k} is larger than the input length n={n}")
def max_sum_fixed(nums: Sequence[int], k: int) -> int:
    """Largest sum of any k consecutive elements.  Theta(n) time, O(1) space."""
    _check_k(len(nums), k)
    window = sum(nums[:k])            # build the first window: k additions
    best = window
    for right in range(k, len(nums)): # slide: one element in, one element out
        window += nums[right] - nums[right - k]
        best = max(best, window)
    return best

I.2 Template 1 in its general form: moving averages

Writing the loop over every index — add, then remove once the window is over-full, then record once it is full — is easier to adapt than the "build first, then slide" version above. It is the same algorithm.

def window_averages(nums: Sequence[float], k: int) -> List[float]:
    """Average of every length-k window (a moving average)."""
    _check_k(len(nums), k)
    out, window = [], 0.0
    for right, x in enumerate(nums):
        window += x                    # element enters on the right
        if right >= k:
            window -= nums[right - k]  # element leaves on the left
        if right >= k - 1:             # window is full -> record it
            out.append(window / k)
    return out

I.3 Variable window, longest: no repeated characters

def longest_unique_substring(s: str) -> int:
    """Length of the longest substring with no repeated character."""
    last_seen = {}          # char -> most recent index
    left = best = 0
    for right, ch in enumerate(s):
        if ch in last_seen and last_seen[ch] >= left:
            left = last_seen[ch] + 1      # jump past the earlier copy
        last_seen[ch] = right
        best = max(best, right - left + 1)
    return best

The jump left = last_seen[ch] + 1 replaces a while loop that would remove characters one by one. Both are Θ(n), but the jump does fewer dictionary operations. The guard last_seen[ch] >= left is essential (Figure F.2).

I.4 Variable window, shortest: sum at least target

def min_len_subarray_at_least(target: int, nums: Sequence[int]) -> int:
    """Shortest subarray with sum >= target (all nums must be positive).
    Returns 0 when no such subarray exists (LeetCode 209 convention)."""
    if any(x <= 0 for x in nums):
        raise ValueError("this sliding window requires strictly positive numbers")
    left = window = 0
    best = float("inf")
    for right, x in enumerate(nums):
        window += x                          # expand
        while window >= target:              # valid -> shrink while still valid
            best = min(best, right - left + 1)
            window -= nums[left]
            left += 1
    return 0 if best == float("inf") else best

The positivity check is error handling for a correctness precondition: with a zero or negative element the shrink logic of G.2 no longer holds, so the function refuses rather than return a wrong answer. For negative inputs, see the deque-over-prefix-sums solution in Section M.

I.5 Variable window, count: at most K distinct, and exactly K

def longest_at_most_k_distinct(nums: Sequence, k: int) -> int:
    """Longest window containing at most k distinct values."""
    if k < 0:
        raise ValueError("k must be non-negative")
    count = Counter()
    left = best = 0
    for right, x in enumerate(nums):
        count[x] += 1
        while len(count) > k:                # invalid -> shrink until valid
            count[nums[left]] -= 1
            if count[nums[left]] == 0:
                del count[nums[left]]
            left += 1
        best = max(best, right - left + 1)
    return best
def count_at_most_k_distinct(nums: Sequence, k: int) -> int:
    """Number of subarrays with at most k distinct values."""
    if k < 0:
        return 0
    count = Counter()
    left = total = 0
    for right, x in enumerate(nums):
        count[x] += 1
        while len(count) > k:
            count[nums[left]] -= 1
            if count[nums[left]] == 0:
                del count[nums[left]]
            left += 1
        total += right - left + 1            # every start in [left, right] works
    return total
def count_exactly_k_distinct(nums: Sequence, k: int) -> int:
    """exactly(k) = atMost(k) - atMost(k-1)."""
    return count_at_most_k_distinct(nums, k) - count_at_most_k_distinct(nums, k - 1)

I.6 Monotonic deque: maximum of every window

def sliding_window_max(nums: Sequence[int], k: int) -> List[int]:
    """Maximum of every length-k window.  Theta(n) time, O(k) extra space."""
    _check_k(len(nums), k)
    dq = deque()            # indices; their values are strictly decreasing
    out = []
    for right, x in enumerate(nums):
        while dq and nums[dq[-1]] <= x:      # x dominates smaller/equal values
            dq.pop()
        dq.append(right)
        if dq[0] <= right - k:               # front index has left the window
            dq.popleft()
        if right >= k - 1:
            out.append(nums[dq[0]])
    return out
LineWhy it is there
dq = deque()Holds indices, so the front's position can be checked against the window's left edge [2].
while dq and nums[dq[-1]] <= x: dq.pop()Removes dominated candidates (G.4). Using <= also removes equal older values, which keeps the deque strictly decreasing.
if dq[0] <= right - k: dq.popleft()At most one index can expire per step, because exactly one index (right − k) leaves per slide.
out.append(nums[dq[0]])The front is the maximum by the invariant.

I.7 Fixed window with a frequency table: anagram positions

def find_anagrams(s: str, p: str) -> List[int]:
    """Start indices of every substring of s that is a permutation of p."""
    k = len(p)
    if k == 0 or k > len(s):
        return []
    need = Counter(p)
    have = Counter()
    out = []
    for right, ch in enumerate(s):
        have[ch] += 1
        if right >= k:                       # drop the outgoing character
            left_ch = s[right - k]
            have[left_ch] -= 1
            if have[left_ch] == 0:
                del have[left_ch]            # keep the Counter comparable
        if have == need:                     # O(alphabet) comparison
            out.append(right - k + 1)
    return out

del have[left_ch] keeps the two Counters comparable with ==. Comparing two Counters costs O(number of keys), bounded by the alphabet size. For huge alphabets, keep an integer matches that counts letters whose needed and current counts agree, and update it in O(1) per step.

I.11 Built-in Python alternatives

  • collections.deque(maxlen=k) keeps the last k items automatically: when a bounded deque is full, appending discards an item from the opposite end [9]. It is ideal for "last k events" buffers.
  • itertools recipe sliding_window(iterable, n) yields overlapping fixed-length tuples using exactly that bounded deque: sliding_window('ABCDEFG', 3) → ABC BCD CDE DEF EFG [10]. Building each tuple costs O(k), so use it to see windows, not to aggregate big ones.
  • itertools.pairwise (Python 3.10+) is the k = 2 special case: successive overlapping pairs [10].
  • numpy.lib.stride_tricks.sliding_window_view (NumPy 1.20+) returns a read-only view of every window without copying data [12]. Reductions over it are vectorised but still Θ(n·k); the documentation notes this generic approach can be far slower than a specialised algorithm for large windows [12].
def sliding_window(iterable: Iterable, k: int) -> Iterator[tuple]:

        raise ValueError("k must be positive")
    it = iter(iterable)
    win = deque(maxlen=k)
    for x in it:
        win.append(x)        # maxlen evicts the oldest item automatically
        if len(win) == k:

        raise TypeError("k must be an int")
    if k <= 0:
        raise ValueError("k must be positive")
    if k > n:

def max_sum_fixed(nums: Sequence[int], k: int) -> int:
    """Largest sum of any k consecutive elements.  Theta(n) time, O(1) space."""
    _check_k(len(nums), k)
    window = sum(nums[:k])            # build the first window: k additions
    best = window
    for right in range(k, len(nums)): # slide: one element in, one element out
        window += nums[right] - nums[right - k]
        best = max(best, window)
    return best


def window_averages(nums: Sequence[float], k: int) -> List[float]:
    """Average of every length-k window (a moving average)."""
    _check_k(len(nums), k)
    out, window = [], 0.0
    for right, x in enumerate(nums):
        window += x                    # element enters on the right
        if right >= k:
            window -= nums[right - k]  # element leaves on the left
        if right >= k - 1:             # window is full -> record it
            out.append(window / k)
    return out

JReal-world applications

Only applications where a window over a sequence is the actual mechanism are listed here. Each entry says which part of the chapter it uses.

J.1 Networking: TCP flow control

TCP numbers every byte. The receiver advertises in each segment a window: the number of data octets, starting from the acknowledged one, that it is willing to accept [13]. The sender keeps SND.UNA (oldest unacknowledged), SND.NXT (next to send) and SND.WND (send window), and RFC 9293's Figure 3 splits the sequence space into four regions, region 3 being the send window [13]. As acknowledgements arrive, SND.UNA moves right and the window slides along the byte stream — a variable-size window whose left end only advances.

J.2 Backend engineering: sliding-window rate limiting

Cloudflare described a rate limiter that approximates "requests in the last 60 seconds" with only two counters per key: the previous minute's count, weighted by how much of it still overlaps the sliding window, plus the current minute's count. Their worked example, with a limit of 50 requests per minute, 42 requests in the previous minute and 18 in the 15 seconds of the current one, estimates 42 × (45/60) + 18 = 49.5 [14]. Measured on 400 million requests from 270,000 sources, 0.003% of requests were wrongly allowed or rate-limited, and the approach needed far less memory than storing a timestamp per request [14].

J.3 Distributed systems and stream processing: windowed aggregation

Apache Flink assigns stream elements to windows. Tumbling windows have a fixed size and do not overlap; sliding windows have a size and a slide interval, overlap when the slide is smaller than the size, and then assign each element to several windows [15]. A "5-minute average every minute" is exactly a fixed window advanced in steps, and incremental (add/remove) aggregation is how such systems avoid recomputing each window. In the theory of data streams, the sliding-window model keeps only the last N elements relevant [23][17].

J.4 Databases: SQL window frames

PostgreSQL's window functions accept a frame clause such as ROWS BETWEEN 2 PRECEDING AND CURRENT ROW. The frame is the set of rows, a subset of the partition, that the function acts on, and it moves with the current row [16]. A 3-row moving average is therefore a fixed-size sliding window written declaratively:

SELECT day, revenue,
       AVG(revenue) OVER (ORDER BY day
                          ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS avg_3d
FROM daily_sales;

The documentation also notes that frames near the partition edges contain fewer rows [16] — the SQL equivalent of the "window not yet full" check in Template 1.

J.5 Search, security and storage: rolling hashes over text

Substring search sits at network choke points and in spam and forensics tools; Princeton's algorithms course lists such applications for substring search and presents Rabin–Karp as its rolling-fingerprint method [7][6]. Each length-m window of the text is hashed in O(1) from the previous one (G.6), so all candidate positions cost O(n) hash updates [8][5]. The same exercise list shows how to extend it to searching for several equal-length patterns at once by storing their hashes in a set [6].

J.6 Image and signal processing: running max/min filters

Morphological dilation and erosion take the maximum or minimum over a sliding neighbourhood. MATLAB's imdilate and imerode use van Herk's algorithm, so the time for a flat rectangular structuring element does not depend on its size [21][19]. The 1-D core is exactly "maximum of every window", solved without a deque by block-wise prefix and suffix maxima (Section N) [20].

J.7 Operating systems and monitoring

Illustration Dashboards that show "error rate over the last 5 minutes" or "p99 latency over the last 1,000 requests" maintain fixed windows over event streams; a deque(maxlen=1000) or a ring buffer plus running counters is the in-process version of Template 1. This is a design pattern rather than a claim about any specific product.

K.3 When to avoid a sliding window

  • The answer may skip elements (subsequences): use DP, sorting or greedy methods instead.
  • The condition is not monotone in L for fixed R (sums with negatives, "exactly K" conditions — unless rewritten as atMost(K) − atMost(K−1)).
  • Many queries with arbitrary, unrelated ranges: use prefix sums, sparse tables or segment trees.
  • The window state cannot be updated cheaply (median without a balanced structure, or the full sorted order of the window).

L.1 Hidden O(k) work inside the loop

✗ Looks like a window, is brute force 
for i in range(n - k + 1):
    best = max(best, sum(a[i:i + k]))  # O(k) copy + sum
Θ(n·k): the slice copies k elements every iteration [11].
✓ Update, don't recompute 
s = sum(a[:k]); best = s
for r in range(k, n):
    s += a[r] - a[r - k]
    best = max(best, s)
Θ(n).

L.2 if instead of while when shrinking

✗ Shrinks at most once per step 
if len(count) > k:      # may still be invalid!
    count[a[L]] -= 1
    if count[a[L]] == 0: del count[a[L]]
    L += 1
total += R - L + 1
Counting windows with at most 1 distinct value in [1, 1, 2]: at R = 2 one removal leaves [1, 2], still invalid, and 2 is added. Result 5; the correct answer is 4.
✓ Repair until valid 
while len(count) > k:
    count[a[L]] -= 1
    if count[a[L]] == 0: del count[a[L]]
    L += 1
total += R - L + 1
Gives 4 (verified by running both versions).

For "longest window" problems only, an if happens to give the right length: the window then never shrinks, only slides, and keeps the best size found so far. This "non-shrinking window" is a known trick, but the window it holds may be invalid, so it is wrong for counting, for "shortest" and for reporting the window itself. Use while unless you can explain why if is safe.

L.3 Forgetting to delete zero counts

count[x] -= 1 leaves the key in the dictionary with value 0, so len(count) still counts x as present. Either del count[x] at zero, or track a separate distinct integer that changes when a count goes 0 → 1 or 1 → 0.

L.4 Off-by-one in the window length and the full-window test

✗ Typical slips 
length = R - L          # one too small
if R >= k:  record()   # skips the first window
remove(a[R - k + 1])     # removes an element still inside
✓ Inclusive window [L, R] 
length = R - L + 1
if R >= k - 1: record() # first full window at R = k-1
remove(a[R - k])         # the element that just left

L.5 Moving L backwards

In the last-seen trick, L = last_seen[ch] + 1 without the guard last_seen[ch] ≥ L (or without L = max(L, last_seen[ch] + 1)) fails on "abba": at the final a, last_seen is 0 while L is 2, so L would jump back to 1 and report length 3 instead of 2.

L.6 Using a list as the deque

window.pop(0) on a list is O(n) because every remaining element moves; collections.deque.popleft() is O(1) [9]. The bug is invisible on small tests and turns Θ(n) into Θ(n·k) on large ones.

L.7 Complexity misconceptions

  • "Nested loops mean O(n²)." Not when the inner loop advances a pointer that never resets. The inner while runs at most n times in total (G.3).
  • "The deque solution is O(n·k) because one step can pop k elements." Each element is popped at most once overall, so the total is O(n) (G.4).
  • "Sliding window is O(1) space." Only for invertible aggregates. Count maps need O(Σ); deques need O(k).
  • "NumPy's sliding_window_view makes it O(n)." The view is free; summing it is still Θ(n·k) arithmetic [12].

L.8 Interview mistakes

  • Not asking whether numbers can be negative or zero — this decides between a window and prefix sums.
  • Recording the answer in the wrong place (before repairing for "longest", after shrinking for "shortest").
  • Returning inf or float('inf') when no window exists instead of the specified 0 or −1.
  • Not stating the invariant out loud. Saying "after this loop, the window [L, R] is the widest valid window ending at R" earns credit even before the code works.

def min_window(s, t):                               # LC 76

        need[ch] -= 1                               # may go negative = surplus

Hint 1Work on prefix sums P. You want the largest i < j with P[j] − P[i] ≥ K.
Hint 2If P[i₁] ≥ P[i₂] with i₁ < i₂, then i₁ is never a better start than i₂, so keep the start candidates in a deque with increasing P. Once a start has served some j, it can be discarded, because later j's would only give longer subarrays.
Solution · Θ(n) time, O(n) space
def shortest_subarray(nums, k):                     # LC 862 (negatives allowed)
    P = [0, *accumulate(nums)]                      # prefix sums, P[0] = 0
    dq = deque(); best = float("inf")
    for j, pj in enumerate(P):
        while dq and pj - P[dq[0]] >= k:            # best start for this end found
            best = min(best, j - dq.popleft())
        while dq and P[dq[-1]] >= pj:               # keep prefix values increasing
            dq.pop()
        dq.append(j)
    return -1 if best == float("inf") else best

M.4 Pattern: deque-optimised dynamic programming

When a DP transition takes the best value from a sliding range of earlier states — dp[i] = nums[i] + max(dp[i−k..i−1]) — the range maximum is a sliding-window maximum, and the DP drops from O(n·k) to O(n). LeetCode 1696 (Jump Game VI) is the standard example [22]:

def max_result(nums, k):                            # LC 1696 Jump Game VI (deque DP)
    dp = [0] * len(nums); dp[0] = nums[0]; dq = deque([0])
    for i in range(1, len(nums)):
        if dq[0] < i - k: dq.popleft()
        dp[i] = nums[i] + dp[dq[0]]
        while dq and dp[dq[-1]] <= dp[i]: dq.pop()
        dq.append(i)
    return dp[-1]

N.1 Any associative aggregate: the two-stack queue

The deque trick is specific to min and max. For any associative operation — gcd, bitwise AND/OR, matrix products — a window can be kept as a queue built from two stacks, where each stack entry also stores the aggregate of itself and everything below it. Push onto the "in" stack; pop from the "out" stack; when "out" is empty, move everything across, which reverses the order. The window aggregate is the combination of the two stack tops. Each element moves between stacks once, so every operation is amortized O(1) [4]. Unlike the deque method, this needs no inverse and no ordering — only associativity.

from math import gcd

class AggQueue:
    """Queue with O(1) amortized push, pop and aggregate for an associative op."""
    def __init__(self, op):
        self.op, self.inn, self.out = op, [], []   # stacks of (value, aggregate)
    def push(self, x):
        agg = x if not self.inn else self.op(self.inn[-1][1], x)
        self.inn.append((x, agg))
    def pop(self):
        if not self.out:                           # move and reverse
            while self.inn:
                x, _ = self.inn.pop()
                agg = x if not self.out else self.op(x, self.out[-1][1])
                self.out.append((x, agg))
        return self.out.pop()[0]
    def query(self):
        parts = [s[-1][1] for s in (self.out, self.inn) if s]
        return parts[0] if len(parts) == 1 else self.op(parts[0], parts[1])

# gcd of every window of size 3 in [12, 18, 24, 9, 27, 36]  ->  [6, 3, 3, 9]

The order inside op(...) keeps "older on the left" for operations that are associative but not commutative, such as matrix products. The example output was verified by running the class.

N.2 Size-independent running max/min: van Herk / Gil–Werman

Split the array into blocks of length k. Inside each block compute prefix maxima left-to-right (g) and suffix maxima right-to-left (h). Any window of length k crosses at most one block boundary, so its maximum is max(h[i], g[i+k−1]). That is O(1) per window with no data-dependent branching, which suits vector hardware and image filters [19][20]. Lemire later gave a streaming variant that uses no more than three comparisons per element [20].

N.3 Order statistics: sliding median and k-th largest

The median has no O(1) update. Standard approaches keep the window in two heaps (a lower max-heap and an upper min-heap) with lazy deletion, or in a balanced binary search tree or sorted container, for O(log k) per slide and O(n log k) overall. LeetCode 480 (Sliding Window Median) is the usual exercise.

N.4 Two-dimensional windows

The maximum over every k×k block of an image is separable: first run the 1-D window maximum along every row, then along every column of that result. The cost is O(rows·cols) whatever k is, which is how a rectangular dilation can be computed in time independent of the structuring element's size [21]. Sums over 2-D windows are easiest with a 2-D prefix-sum table (Chapter 03).

N.5 Streaming windows in sub-linear memory

Sometimes even the window is too large to store — think of counting the 1s in the last billion bits of a network stream. Datar, Gionis, Indyk and Motwani's exponential histograms keep buckets whose sizes are powers of two and approximate the count within a factor 1 ± ε using O((1/ε) log² N) bits, and they show this is essentially optimal [17]. Mining of Massive Datasets (Stanford) teaches the same algorithm under the name DGIM [18]. The general lesson: exact sliding windows need memory proportional to the window, and approximation buys space, just as Cloudflare's two-counter estimate does [14].

N.6 Time-based and event-time windows

In production, windows are often defined by time ("last 5 minutes") rather than by count, and events can arrive out of order. Stream processors such as Flink distinguish tumbling, sliding, session and global windows and let you choose processing time or event time [15]. The algorithmic core is unchanged — evict what fell out of the window, fold in what arrived — but eviction is now driven by timestamps and watermarks instead of by an index.

Detailed revision notes

1 · Formal definition

A window is [L, R], 0 ≤ L ≤ R < n, length R − L + 1. A sliding-window algorithm visits windows with non-decreasing L and R and keeps a state updated by add(a[R]) / remove(a[L]).

2 · Core concept

Neighbouring windows share k − 1 elements → update instead of recompute. Fixed: S′ = S − a[L] + a[R+1] (needs an inverse). Variable: grow with R, repair with L.

3 · Key properties

① each pointer moves ≤ n times → ≤ 2n state updates → Θ(n) amortized.
② variable windows need a monotone condition (shrink-closed: sub-window of valid is valid).
③ L*(R) is non-decreasing (staircase picture, Fig. G.1).
④ count valid windows ending at R = R − L + 1.

4 · Operations & state

sum/count/xor → 1 integer · distinct/anagram → dict of counts (delete zeros!) · max/min → monotonic deque of indices · gcd/AND/OR → two-stack queue.

5 · Python syntax

from collections import deque, Counter

deque(maxlen=k) = last k items · itertools.pairwise = k = 2
never sum(a[i:i+k]) in the loop · never list.pop(0)

6 · Applications

TCP send window (SND.UNA … SND.UNA+SND.WND) · rate limit ≈ prev × overlap + curr · Flink sliding windows · SQL frames · Rabin–Karp rolling hash · running max/min image filters.

P.5 Answer key

Conceptual answers
  1. The update removes the leaving element's contribution by applying an inverse: −x for +, x itself for xor (x ⊕ x = 0). Maximum has no inverse — knowing max(window) and the leaving value tells you nothing about the new maximum if the leaving value was the maximum — so a structure that remembers the runner-up candidates (the monotonic deque) is needed (G.1, G.4).
  2. R increases from 0 to n−1 once. L starts at 0, only increases, and never exceeds n, so across the entire run the while body executes at most n times. Total body executions ≤ n (for) + n (while) = 2n, each O(1) (aggregate amortized analysis, G.3).
  3. Shrink-closed: "at most K distinct", "no repeated character", "sum ≤ T with non-negative values". Not shrink-closed: "exactly K distinct", "sum ≥ T" (removing elements can make it invalid), "sum = T" with negatives. Shrink-closure makes L*(R) monotone, so L never needs to move back; without it, the correct left end can jump backwards and the two-pointer scan misses answers (G.2, K.2).
  4. To detect expiry: the front must leave when its position is ≤ R − k. With values only, duplicates make it impossible to tell which copy is leaving (CP-Algorithms' value-only variant must compare against the removed value, and the index-based variant avoids that) [4][2].
  5. With negative values, shrinking can increase the sum, so "valid" is not monotone and the window can stop shrinking too early — see the counterexample [84, −37, 32, 40, 95], K = 167 in K.2. Use prefix sums with a monotonic deque (LeetCode 862, Section M) for O(n).

def contains_nearby_duplicate(nums, k):             # LC 219 (assessment coding 1)
    window = set()
    for i, x in enumerate(nums):
        if x in window: return True
        window.add(x)
        if len(window) > k: window.remove(nums[i - k])
    return False

Fixed window kept as a set of the last k values · O(n) expected time, O(k) space.

def count_subarrays_product_less(nums, k):          # LC 713 (assessment coding 2)
    if k <= 1: return 0
    prod = 1; left = total = 0
    for right, x in enumerate(nums):
        prod *= x
        while prod >= k:
            prod //= nums[left]; left += 1
        total += right - left + 1
    return total

def sliding_window_min_range(nums, k):              # assessment coding 3: max-min per window
    mx, mn, out = deque(), deque(), []
    for r, x in enumerate(nums):
        while mx and nums[mx[-1]] <= x: mx.pop()
        while mn and nums[mn[-1]] >= x: mn.pop()
        mx.append(r); mn.append(r)
        if mx[0] <= r - k: mx.popleft()
        if mn[0] <= r - k: mn.popleft()
        if r >= k - 1: out.append(nums[mx[0]] - nums[mn[0]])
    return out

Two monotonic deques, one for the maximum and one for the minimum · O(n) time, O(k) space.

Engineering scenario: a model answer
  1. Window choice. A fixed-window counter (reset each minute) lets an attacker send 30 failures at 0:59 and 30 more at 1:00 — 60 in two seconds — without tripping the rule. A sliding log of timestamps is exact but costs one entry per failure. A sliding counter stores two integers per IP (previous and current minute) and estimates prev × (1 − elapsed/60) + curr, which is the approach Cloudflare measured as very accurate at scale [14].
  2. State placement. Requests for an IP reach any instance, so per-instance memory sees only part of the traffic — the same problem Cloudflare describes for edge servers [14]. Keep the counters in a shared store keyed by (ip, minute), using atomic increments and a TTL of about two minutes, so old minutes expire on their own.
  3. Memory. Two small integers per active IP rather than up to 30+ timestamps; only IPs with recent failures have keys at all.
  4. Accuracy. The estimate assumes failures in the previous minute were evenly spread, so it can be slightly off near the threshold. For a security block that is usually acceptable; if exactness matters for a small set of suspicious IPs, switch just those to a sliding log (a deque of timestamps, evicting entries older than 60 s — Template 1 driven by time).
  5. Block action. When the estimate exceeds 30, write a blocked:ip key with a 10-minute TTL and check it before any password verification.
