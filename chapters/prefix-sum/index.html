Prefix Sum — add once, answer forever

Cumulative sums, range queries, the hash-map counting trick, 2D summed-area tables and difference arrays — from first principles to interview-ready patterns.

Difficulty: Beginner → Intermediate (advanced section: Upper-intermediate) Reading time: ~75 minutes (+ 30 min exercises) Language: Python 3.8+

AChapter introduction

Prerequisites

You should be comfortable with Python lists and 0-based indexing, for loops, basic Big-O notation (what O(n) and O(1) mean), and Python dictionaries. No prior knowledge of trees or advanced mathematics is needed; the only formula you must remember fits on one line.

Learning objectives

After completing this chapter you will be able to:

  1. Define a prefix sum array formally and informally, and explain the role of the leading zero (the sentinel).
  2. Answer any contiguous range-sum query in constant time using P[R+1] − P[L], and prove why it is correct.
  3. Analyse the build, query and update costs, and explain exactly when prefix sums stop being the right tool.
  4. Combine prefix sums with a hash map to count or find subarrays with a given property in linear time.
  5. Extend the idea to two dimensions (summed-area tables / integral images) using inclusion–exclusion.
  6. Use the inverse operation — the difference array — to apply many range updates in O(1) each.
  7. Recognise prefix-sum patterns in interview problems, and know the next structures to reach for (Fenwick tree, segment tree, parallel scan).
The one-sentence promise Spend O(n) time once to record running totals, and every later question of the form “what is the sum between positions L and R?” becomes a single subtraction. [2][3]

BFundamental understanding

What is a prefix sum?

Take a list of numbers. Walk through it from left to right, keeping a running total, and write down the total after each step. The list of totals you wrote down is the list of prefix sums (also called cumulative sums or running totals). For the natural numbers 1, 2, 3, 4, 5, 6 the prefix sums are 1, 3, 6, 10, 15, 21 — the triangular numbers. [8]

Formal definition Given a sequence A = [a0, a1, …, an−1] and a binary associative operator ⊕, the all-prefix-sums operation returns [a0, (a0 ⊕ a1), …, (a0 ⊕ a1 ⊕ … ⊕ an−1)]. With ⊕ = +, the input [3 1 7 0 4 1 6 3] yields [3 4 11 11 15 16 22 25]. This is Blelloch’s definition from his 1990 Carnegie Mellon report, where the operation is also called a scan. [1][12]
Simple English definition A prefix sum array answers the question “how much has been added up so far?” for every position. Once you know the “so far” totals, the amount added between two positions is just the later total minus the earlier one.

In algorithm design we almost always use the exclusive, sentinel-padded form, which has one extra slot at the front:

P[0] = 0,    P[i+1] = P[i] + A[i]   for   0 ≤ i < n   ⟹   P[i] = A[0] + A[1] + … + A[i−1]

So P[i] is the sum of the first i elements, and P has length n+1. This is the convention used by CMU’s 15-451 lecture notes, Swarthmore’s competitive programming notes and the USACO Guide. [2][13][3]

Inclusive versus exclusive scans

The two forms differ only in whether element i is included in output i. An inclusive scan gives yi = a0 + … + ai; an exclusive scan gives yi = a0 + … + ai−1 and starts with the identity (0 for addition). They convert into each other by shifting by one position, and real libraries ship both — C++ has std::inclusive_scan and std::exclusive_scan, MPI has MPI_Scan and MPI_Exscan. [8][12] The padded array P above is simply the exclusive scan with the grand total appended at the end.

Why does this concept exist?

Many questions about a sequence are really questions about a contiguous stretch of it: total sales between day 30 and day 90, number of errors logged between two timestamps, how many 1-bits lie in a window. Answering each such question by looping over the stretch costs time proportional to its length. When the data does not change but the questions keep coming, that repeated work is wasted: the same additions are performed again and again. Prefix sums do the additions once and store them so that every future query reuses them. [2]

A little history

The running total is ancient, but the prefix sum as a named algorithmic building block has a well-documented modern history. Parallel prefix methods were studied for binary adder circuits by Ofman (1962) and Khrapchenko (1967); Ladner and Fischer (1980) gave general parallel prefix computation; Hillis and Steele (1986) published a short-span data-parallel algorithm; and Blelloch’s 1990 work made “scan” a primitive of data-parallel programming. [8][1] In computer graphics, Franklin Crow introduced the two-dimensional version — the summed-area table — for texture mapping at SIGGRAPH 1984, and Viola and Jones later popularised it in computer vision as the integral image. [10][9] Fenwick (1994) introduced the binary indexed tree to keep prefix sums under updates. [8][7]

Fundamental principles

Three ideas carry the whole chapter:

  1. Precomputation trades space for time. Store n+1 extra numbers and queries drop from linear to constant time. [2]
  2. Subtraction cancels a shared prefix. The sum of A[L..R] is “everything up to R” minus “everything before L”. This works because addition has an inverse (subtraction). Operators without an inverse — like max — still have prefix scans, but cannot answer arbitrary ranges this way. [1][7]
  3. Prefix sums and differences are inverse operations. Taking adjacent differences of P gives back A; taking prefix sums of a difference array gives back the original — the discrete analogue of integration and differentiation. [14]

CThe problem statement

The Static Range Sum Query problem

ComponentSpecification
InputAn array A of n numbers that does not change, and q queries, each a pair (L, R) with 0 ≤ L ≤ R < n.
OutputFor each query, the value A[L] + A[L+1] + … + A[R].
Typical constraintsCompetitive-programming versions such as CSES “Static Range Sum Queries” use n, q up to 2·105 with values up to 109, so totals exceed 32-bit range. [19]
Key assumptionNo element is modified between queries (a static array). [2]

Why the naive approach is inefficient

The obvious solution loops over positions L to R for each query. That costs Θ(R − L + 1), which is O(n) in the worst case, so q queries cost O(n·q). [2] With n = q = 2·105 that is up to 4·1010 additions — far too slow. In Python, sum(A[L:R+1]) looks like one operation but is not: slicing a list of k items costs O(k) and summing costs another O(k). [16]

Limitations of other approaches

Precomputing every answer in an n × n table gives O(1) queries but needs Θ(n2) memory and time — 4·1010 cells for the constraint above. A segment tree answers queries in O(log n) and also supports updates, but it is more code and slower per query than necessary when the array never changes. [2]

How prefix sums improve the solution

Build P in one O(n) pass, then answer each query with P[R+1] − P[L] in O(1). Total: O(n + q) time and O(n) extra space. For a static array this is essentially optimal, since just reading the input already takes Ω(n + q). [2][3]

Real-world analogy: the odometer A car’s odometer shows the total kilometres driven since the car was built — a prefix sum of every trip. To know how far you drove between Monday morning and Friday evening you do not replay the week’s trips; you subtract Monday’s odometer reading from Friday’s. Recording the reading costs nothing extra while driving (the O(n) build), and every “how far between these two moments?” question becomes one subtraction (the O(1) query). (Illustrative analogy.)

FInternal working

F.1 Memory representation

In Python, both A and P are list objects: contiguous arrays of references to integer objects, so indexing P[k] is O(1). [16] Python integers have unlimited precision, so the running total can never overflow — a real difference from C, Java or NumPy, where a 64-bit accumulator wraps around silently. [17][6] In a low-level language you would choose a wide accumulator type (for example 64-bit) because n · max|A[i]| can exceed the element type’s range even when every element fits. [19]

F.2 Execution flow of the build

  1. Allocate P of length n+1 filled with zeros. P[0] = 0 is now set.
  2. For i = 0, 1, …, n−1: read P[i] (the total so far), read A[i], write P[i+1] = P[i] + A[i].
  3. Stop. P[n] holds the sum of the whole array.

Each iteration reads two values and writes one, in strictly increasing memory order — a single sequential pass that is cache-friendly. The loop has a dependency chain (step i+1 needs step i), which is why the parallel versions in Section N need a cleverer algorithm. [12]

F.3 Execution flow of a query

  1. Validate 0 ≤ L ≤ R < n.
  2. Read P[R+1] (sum of A[0..R]) and P[L] (sum of A[0..L−1]).
  3. Return the difference. No loop, no state change; P is read-only after the build.

F.4 State changes and the cost of an update

If one element changes, A[i] += δ, then every prefix that contains A[i] — that is P[i+1], …, P[n] — must also increase by δ. That is n − i writes, O(n) in the worst case. This is precisely the weakness that motivates Fenwick trees and segment trees. [2][7]

F.5 Pattern: prefix sums + hash map

Many problems ask not for one range but for how many (or the longest/shortest) subarrays satisfy a sum condition. A subarray A[i..j−1] has sum P[j] − P[i], so “sum equals k” becomes “P[i] = P[j] − k for some earlier i”. Scanning left to right, we keep a dictionary seen counting how often each prefix value has occurred; at each new position we look up running − k. This reduces the Θ(n2) pairs to one pass with expected O(1) dictionary operations. [14][16]

F.6 Extension: two dimensions

For a grid G with r rows and c columns, define a padded table S of size (r+1) × (c+1) where S[i][j] is the sum of the rectangle from (0,0) to (i−1, j−1). It is built row by row with

S[i+1][j+1] = G[i][j] + S[i][j+1] + S[i+1][j] − S[i][j]

where the last term removes the corner counted twice. Any rectangle with corners (r1, c1) and (r2, c2) is then answered from four table entries:

sum = S[r2+1][c2+1] − S[r1][c2+1] − S[r2+1][c1] + S[r1][c1]

Building takes O(rc) and each query O(1). [4] In graphics and vision the same table is the summed-area table or integral image: any rectangle sum needs exactly four references, regardless of its size. [9][11]

F.7 Extension: the difference array (the inverse operation)

Prefix sums make range queries cheap. Their inverse makes range updates cheap. Define D[0] = A[0] and D[i] = A[i] − A[i−1]; then the prefix sums of D give back A. [14] To add v to every element of A[l..r], change only two entries: D[l] += v and D[r+1] −= v. After all updates, one prefix-sum pass reconstructs the array. Each update is O(1); the final rebuild is O(n). [4]

F.8 Edge cases

SituationWhat happens with the padded design
Empty array (n = 0)P = [0]; no valid query exists, so the validator must reject every (L, R).
Range starting at 0P[R+1] − P[0] = P[R+1]; the sentinel removes the special case an unpadded array would need. [3]
Single element L = RP[L+1] − P[L] = A[L].
Negative numbersWork unchanged; P is no longer monotonic, so do not binary-search it.
L > R or out of boundsPython negative indices would silently wrap around and return garbage, so validate explicitly.
Floating-point valuesLarge prefixes can absorb small values; differences then suffer cancellation (see Section L). [18]

GMathematical foundation

G.1 Definitions

P[i] = Σk=0i−1 A[k]   (0 ≤ i ≤ n),     with P[0] = 0 (empty sum)

The range sum is S(L, R) = Σk=LR A[k]. Using half-open intervals [i, j), as CMU’s notes do, the formula is the especially clean S[i, j) = P[j] − P[i]. [2]

G.2 The loop invariant and its proof

InvariantAt the start of iteration i of the build loop, P[0..i] are correct: P[t] = Σk<t A[k] for all t ≤ i.

Initialisation. Before iteration 0, only P[0] = 0 is claimed, and the empty sum is 0. ✔
Maintenance. If P[i] = Σk<i A[k], the loop sets P[i+1] = P[i] + A[i] = Σk<i+1 A[k]. ✔
Termination. After iteration n−1, all of P[0..n] are correct. ∎

G.3 Why the query formula is correct (telescoping)

P[R+1] − P[L] = Σk=0R A[k] − Σk=0L−1 A[k] = Σk=LR A[k]

The first L terms appear in both sums and cancel. Equivalently, Σk=LR (P[k+1] − P[k]) is a telescoping sum in which every interior term cancels. This uses two algebraic facts about +: it is associative (so grouping does not matter) and it has an inverse (subtraction). [1]

The inverse requirement mattersAny associative operator has a prefix scan (prefix max, prefix product, prefix XOR, …). [1][8] But only operators with an inverse let you subtract one prefix from another. XOR is its own inverse, so prefix XOR answers range XOR as X[R+1] ⊕ X[L]. Max has no inverse, so prefix max cannot answer an arbitrary range max — that needs a sparse table or segment tree. Products work only if no element is zero (division by zero). CP-Algorithms notes that a Fenwick tree likewise needs an invertible operation for general range queries. [7]

G.4 2D: inclusion–exclusion

Let S(i, j) be the sum of the top-left i × j block. Splitting the block at row i−1 and column j−1 and applying inclusion–exclusion gives the build recurrence S(i, j) = G[i−1][j−1] + S(i−1, j) + S(i, j−1) − S(i−1, j−1); applying it to the query gives the four-term formula in F.6. [4] In d dimensions the same principle uses 2d corner terms with alternating signs. [9]

G.5 Prefix sums and differences are inverses

Define the operators 𝒫 (prefix sum) and 𝒟 (adjacent difference). Then 𝒟(𝒫(A)) = A and 𝒫(𝒟(A)) = A: they are the discrete counterparts of integration and differentiation. [14] A range update “add v on [l, r]” changes the derivative only at the two boundaries — which is exactly why the difference array touches two cells.

G.6 The counting identity behind subarray problems

An array of length n has n(n+1)/2 non-empty contiguous subarrays, one for each pair 0 ≤ i < j ≤ n of prefix positions. A condition on a subarray sum is therefore a condition on a pair of prefix values. “Sum = k” becomes “P[i] = P[j] − k”; “sum divisible by m” becomes “P[i] ≡ P[j] (mod m)”; “maximum sum” becomes “P[j] − mini<j P[i]”. Each converts a quadratic search over pairs into one linear scan with a dictionary or a running minimum. [4][13]

Reasoning behind each entry

Build. The loop runs exactly n times doing constant work, independent of the values, so best, average and worst cases coincide: Θ(n) (both O(n) and Ω(n)). [3] No algorithm can do better, because every element must be read at least once to know the total — a lower bound of Ω(n).

Query. Two reads and one subtraction regardless of L, R: Θ(1). [2]

Update. Changing A[i] invalidates P[i+1..n]: n − i writes. Averaged over uniformly random i that is about n/2, still Θ(n). With roughly equal numbers of updates and queries, the average cost per operation is Θ(n) — CMU’s notes describe this as the point where plain prefix sums stop being adequate. [2]

Hash-map pattern. One pass of n iterations, each doing one lookup and one insert. Python’s dict has O(1) average and O(n) amortised-worst-case cost per operation, so the theoretical worst case is O(n2); in practice, with integer keys and Python’s hashing, the expected Θ(n) is what you observe. [16]

Amortised view and time–space trade-off

If you answer q queries, the one-time Θ(n) build is spread across them: amortised cost per query is Θ(n/q + 1). Prefix sums pay off as soon as you expect more than a handful of queries over long ranges. The trade is n+1 extra numbers of memory; for the 2D case it is a full extra table the size of the grid. Summed-area tables also need more bits per entry than the original data, because the totals grow — Crow’s paper discusses this storage cost for textures. [10]

Theory versus actual Python behaviour

  • Constant factors. A Python-level for loop is interpreted; itertools.accumulate runs the same loop in C, and NumPy’s cumsum runs it over a typed buffer. All three are Θ(n), but the built-ins are usually much faster in wall-clock time. [5][6]
  • Hidden linear costs. sum(A[L:R+1]) is O(R−L) for the slice and O(R−L) for the sum — never constant. [16]
  • Integer size. Python ints never overflow; NumPy integer arithmetic is modular and raises no error on overflow. [17][6]

IPython implementation

I.1 Implementation from scratch

class PrefixSum:
    """Static range-sum structure. Build O(n), query O(1)."""

    def __init__(self, arr):
        self.n = len(arr)
        self.P = [0] * (self.n + 1)          # P[0] = 0 is the sentinel
        for i, x in enumerate(arr):
            self.P[i + 1] = self.P[i] + x    # invariant: P[i+1] = A[0] + ... + A[i]

    def range_sum(self, left, right):
        """Sum of A[left..right], both inclusive (0-indexed)."""
        if not (0 <= left <= right < self.n):
            raise IndexError(f"invalid range [{left}, {right}] for n={self.n}")
        return self.P[right + 1] - self.P[left]


if __name__ == "__main__":
    A = [3, 1, 4, 1, 5, 9, 2, 6]
    ps = PrefixSum(A)
    print("P =", ps.P)
    print("sum(2..5) =", ps.range_sum(2, 5))
    print("sum(0..7) =", ps.range_sum(0, 7))
    print("sum(4..4) =", ps.range_sum(4, 4))
    try:
        ps.range_sum(5, 2)
    except IndexError as e:
        print("IndexError:", e)
    print("empty P =", PrefixSum([]).P)

I.3 Prefix sum + hash map: subarray sum equals k

from collections import defaultdict

def subarray_sum_equals_k(nums, k):
    count = 0
    running = 0
    seen = defaultdict(int)
    seen[0] = 1                      # the empty prefix: lets subarrays start at index 0
    for x in nums:
        running += x
        count += seen[running - k]   # earlier prefixes equal to running-k end a valid subarray here
        seen[running] += 1           # record AFTER the lookup (prevents empty subarrays when k == 0)
    return count

print(subarray_sum_equals_k([1, 2, 3, -2, 2, 1], 3))   # 5

I.4 2D prefix sums

class PrefixSum2D:
    def __init__(self, grid):
        rows = len(grid)
        cols = len(grid[0]) if grid else 0
        self.S = [[0] * (cols + 1) for _ in range(rows + 1)]   # zero row + zero column
        for r in range(rows):
            for c in range(cols):
                self.S[r + 1][c + 1] = (grid[r][c] + self.S[r][c + 1]
                                        + self.S[r + 1][c] - self.S[r][c])

    def region_sum(self, r1, c1, r2, c2):
        """Sum of grid[r1..r2][c1..c2], all bounds inclusive."""
        S = self.S
        return S[r2 + 1][c2 + 1] - S[r1][c2 + 1] - S[r2 + 1][c1] + S[r1][c1]

G = [[3, 0, 1, 4, 2],
     [5, 6, 3, 2, 1],
     [1, 2, 0, 1, 5],
     [4, 1, 0, 1, 7]]
print(PrefixSum2D(G).region_sum(1, 1, 2, 3))   # 14

Note [[0] * (cols + 1) for _ in range(rows + 1)]: writing [[0] * (cols + 1)] * (rows + 1) instead would create one row object referenced many times — a classic Python aliasing bug. Build Θ(rc), query Θ(1). [4]

I.5 Difference array

def apply_range_updates(n, updates):
    """updates: list of (l, r, v) meaning add v to A[l..r] inclusive. Start from zeros."""
    diff = [0] * (n + 1)               # one spare slot so r + 1 == n is safe
    for l, r, v in updates:
        if not (0 <= l <= r < n):
            raise IndexError(f"bad update range [{l}, {r}]")
        diff[l] += v
        diff[r + 1] -= v
    out, running = [], 0
    for i in range(n):                 # prefix-sum the difference array
        running += diff[i]
        out.append(running)
    return out

print(apply_range_updates(6, [(1, 3, 2), (2, 5, 3), (0, 1, -1)]))  # [-1, 1, 5, 5, 3, 3]

Time Θ(u + n) for u updates; space Θ(n). [4][14]

JReal-world applications

Only applications with a direct, documented use of prefix sums are listed. Where a scenario is our own illustration rather than a cited system, it is marked as such.

J.1 Computer vision and graphics: integral images

Viola and Jones’ real-time face detector evaluates a large number of rectangle (Haar-like) features in every image window. They introduced the integral image — a 2D prefix sum computed in a few operations per pixel — so that each rectangle feature can be evaluated in constant time at any scale or location; they credit Crow’s 1984 summed-area tables as the graphics precursor. [11][10] Crow’s original use was texture filtering: averaging a texture over a rectangle at a cost independent of the rectangle’s size. [10]

J.2 Databases and analytics: running totals

SQL window functions compute prefix sums declaratively. PostgreSQL’s tutorial shows sum(salary) OVER (ORDER BY salary) producing a running total, because with ORDER BY the default frame runs from the start of the partition through the current row (plus peers with equal sort keys). [21] Backend reporting code (cumulative revenue, cumulative sign-ups, “month-to-date” dashboards) uses exactly this, and the subtraction trick turns two cumulative values into any period total.

J.3 Search engines: decoding gap-encoded postings lists

Inverted indexes store each term’s sorted list of document IDs. Because consecutive IDs are close together, indexes store the gaps between them (for example 107, 5, 43 instead of 283154, 283159, 283202), which need far fewer bits. [22] Recovering the actual IDs is a prefix sum over the gaps — the gap list is a difference array, and decoding is its inverse.

J.4 Sorting and systems: computing output positions

Counting sort counts how many items have each key and then takes cumulative sums of the counts; the cumulative sum for a key tells you where that key’s block begins in the output. MIT 6.006 implements counting sort this way, and radix sort uses it as a stable subroutine. [15][8] The same “prefix sum of sizes gives offsets” idea appears whenever variable-sized records are packed contiguously into a buffer.

J.5 Parallel and distributed computing: scan as a primitive

Blelloch showed that many parallel algorithms — split radix sort, quicksort, line drawing, minimum spanning tree — can be built from scan operations, and the Connection Machine supported scans directly. [1] On GPUs, parallel scan underlies stream compaction, radix sort and summed-area tables. [12] In distributed-memory programs, MPI provides MPI_Scan and MPI_Exscan so that each process can learn the total of the values held by the processes before it — e.g. to compute its write offset into a shared output file. [8]

J.6 Compression and data structures for dynamic data

When counts change over time (for example cumulative frequency tables whose counts keep changing), the static array is replaced by a Fenwick tree, which keeps prefix sums queryable and updatable in O(log n); Fenwick introduced it for cumulative frequency tables. [8][7] Pibiri and Venturini’s study of the prefix-sum problem benchmarks such structures because they sit inside many larger systems. [23]

Engineering illustration (our example)A web API logs one integer per minute: requests served. Product managers ask ad-hoc questions like “how many requests between 09:15 and 11:40 yesterday?”. Store the day’s 1,440 per-minute counts plus a 1,441-entry cumulative array; each question becomes one subtraction instead of a scan, and the cumulative array is computed once when the day closes (the data are static afterwards).

When to avoid prefix sums

  • The array is updated frequently between queries (rebuild or fix-up costs O(n)). [2]
  • The query operator has no inverse (min, max, gcd) — subtraction of prefixes is meaningless.
  • Only one or two queries will ever be asked: the build costs as much as the naive answer.
  • Floating-point data with huge dynamic range, where cancellation can destroy small range sums (Section L).

LCommon mistakes and misconceptions

L.1 Off-by-one: mixing inclusive and exclusive conventions

✗ Incorrect
# P is the padded array (len n+1)
def range_sum(P, L, R):
    return P[R] - P[L]      # misses A[R]!
✓ Correct
# P[k] = sum of first k elements
def range_sum(P, L, R):
    return P[R + 1] - P[L]  # inclusive L..R

Pick one convention and write it as a comment beside the array. With the padded array, “inclusive [L, R]” is P[R+1] − P[L] and “half-open [i, j)” is P[j] − P[i]. [2]

L.2 Unpadded arrays and the L = 0 special case

✗ Incorrect
pre = list(accumulate(A))      # inclusive, no sentinel
def range_sum(L, R):
    return pre[R] - pre[L - 1]  # L = 0 reads pre[-1]: the LAST element!
✓ Correct
P = list(accumulate(A, initial=0))
def range_sum(L, R):
    return P[R + 1] - P[L]      # L = 0 just reads P[0] = 0

Python’s negative indexing turns this bug into a wrong number instead of a crash, which makes it especially dangerous.

L.3 Counting the empty prefix (forgetting seen[0] = 1)

In the hash-map pattern, omitting the initial entry for prefix value 0 misses every valid subarray that starts at index 0. For nums = [3], k = 3 the buggy version returns 0 instead of 1. Similarly, inserting running into the dictionary before looking up running − k counts the empty subarray when k = 0.

L.4 Using a sliding window when values can be negative

Two-pointer windows assume that extending the window never decreases its sum. With negatives (e.g. [1, −1, 1], k = 1) that assumption fails and windows are missed. The prefix + hash map approach does not rely on monotonicity.

L.5 Complexity misconceptions

  • “sum(A[L:R+1]) is O(1) because it’s one line.” It is O(R − L): list slicing copies k elements. [16]
  • “Prefix sums make range updates fast.” No — they make queries fast; updates become O(n). Difference arrays are the update-friendly dual. [2][4]
  • “Rebuilding P inside the query loop is fine.” That silently reintroduces O(nq).
  • “The hash-map solution is O(n) worst case.” It is O(n) expected; dictionary operations have an O(n) worst case. [16]

L.6 Overflow and precision

Python ints never overflow, but NumPy and fixed-width languages do. The output below was produced by running the code:

import numpy as np
np.cumsum(np.array([2**62, 2**62], dtype=np.int64))
# array([ 4611686018427387904, -9223372036854775808])   <- wrapped silently

from itertools import accumulate
P = list(accumulate([1e16, 1.0, -1e16, 1.0], initial=0.0))
P[2] - P[1]      # 0.0, but A[1] is 1.0 (absorbed: 1e16 + 1.0 == 1e16 in float64)

NumPy documents that integer arithmetic is modular and raises no error on overflow. [6] For floats, prefer integer units (cents, not dollars) or accurate summation such as math.fsum, which tracks multiple partial sums to avoid loss of precision. [18]

L.7 2D mistakes

  • Forgetting to add back the overlap + S[r1][c1] (double subtraction).
  • Creating rows with [[0]*(c+1)]*(r+1) — all rows alias the same list.
  • Swapping row/column order in the formula when the grid is not square.

L.8 Interview mistakes

  • Jumping to code without stating the convention (inclusive/exclusive, padded or not).
  • Not asking whether values can be negative or zero — this decides sliding window vs prefix + hash map.
  • Not mentioning the update cost when the interviewer adds “and the array can change”: the expected answer is “then I would switch to a Fenwick or segment tree.”

H1. Number of Submatrices That Sum to Target Hard — LeetCode 1074

HintFix a pair of rows (top, bottom); collapse the strip into a 1D array of column sums; then it is exactly Subarray Sum Equals K.
Optimised solution 
from collections import defaultdict
def num_submatrix_sum_target(matrix, target):
    R, C = len(matrix), len(matrix[0])
    ans = 0
    for top in range(R):
        col = [0] * C
        for bottom in range(top, R):
            for c in range(C):
                col[c] += matrix[bottom][c]      # column sums of the strip
            seen = defaultdict(int); seen[0] = 1
            running = 0
            for v in col:                        # 1D subarray-sum-equals-k
                running += v
                ans += seen[running - target]
                seen[running] += 1
    return ans

Θ(R²·C) expected time, O(C) space (transpose first if R > C).

H2. Shortest Subarray with Sum at Least K Hard — LeetCode 862

HintNegatives allowed. Over prefix values, keep a deque of indices with increasing P: pop from the front while P[j] − P[front] ≥ k (record length), pop from the back while P[back] ≥ P[j].
Optimised solution 
from collections import deque
from itertools import accumulate
def shortest_subarray(nums, k):
    P = list(accumulate(nums, initial=0))
    best = len(nums) + 1
    dq = deque()
    for j, pj in enumerate(P):
        while dq and pj - P[dq[0]] >= k:
            best = min(best, j - dq.popleft())
        while dq and P[dq[-1]] >= pj:
            dq.pop()
        dq.append(j)
    return best if best <= len(nums) else -1

Θ(n) time: each index enters and leaves the deque at most once. Space Θ(n).

NAdvanced concepts

This section shows how the simple running total grows into more powerful structures. Skim it on a first reading; return when you meet problems with updates or parallel hardware.

N.1 Prefix sums under updates: the Fenwick tree

The static array fails when values change, because one update touches O(n) prefixes. A Fenwick tree (binary indexed tree) stores, at index i, the sum of a block that ends at i and whose length is the lowest set bit of i. Any prefix is the sum of O(log n) such blocks, and any element lies in O(log n) blocks, so both prefix queries and point updates cost O(log n) with O(n) memory. [7][8]

class Fenwick:
    """1-indexed binary indexed tree for prefix sums with point updates."""
    def __init__(self, n):
        self.n = n
        self.tree = [0] * (n + 1)

    def add(self, i, delta):          # A[i] += delta, 1-indexed
        while i <= self.n:
            self.tree[i] += delta
            i += i & -i               # jump to the next block that contains i

    def prefix(self, i):              # A[1] + ... + A[i]
        s = 0
        while i > 0:
            s += self.tree[i]
            i -= i & -i               # strip the lowest set bit
        return s

    def range_sum(self, l, r):        # inclusive, 1-indexed
        return self.prefix(r) - self.prefix(l - 1)

A segment tree generalises further: it supports updates with non-invertible operators such as min and max, and with lazy propagation it supports range updates with range queries. [2]

N.2 Parallel prefix sums (scan)

The sequential loop has a dependency chain, so it looks impossible to parallelise; Blelloch called the operation a good example of a computation that seems inherently sequential yet has an efficient parallel algorithm. [1][12] Two classic schemes:

  • Hillis–Steele: in round d, every element adds the value 2d positions to its left. After ⌈log₂ n⌉ rounds the scan is done, but the total work is O(n log n) — not work-efficient. [12][8]
  • Work-efficient (up-sweep / down-sweep): build a reduction tree bottom-up, then push partial sums down. It does O(n) work with about 2 log₂ n steps, and is the basis of the GPU implementation in GPU Gems 3. [1][12][20]

N.3 Other invertible operators

  • Prefix XOR: X[R+1] ⊕ X[L] gives range XOR, since XOR is its own inverse.
  • Prefix counts: one prefix array per category (e.g. 26 for letters) answers “how many of each letter in s[l..r]?” in O(1) per letter. [3]
  • Modular prefix sums: remainders mod m, as in LeetCode 974.
  • Higher-order integral images: storing prefix sums of x and of x² gives the variance of any rectangle in O(1). [9]

N.4 2D difference arrays and the “imos” method

Range updates on rectangles work like the 1D case with four marks: +v at (r1, c1), −v at (r1, c2+1) and (r2+1, c1), +v at (r2+1, c2+1); a 2D prefix pass then materialises the grid. USACO’s “Painting the Barn” is the standard practice problem. [4]

N.5 Prefix sums on trees and lists

The same idea applies to root-to-node paths: store the sum from the root to each node; the sum of a path between u and v is pre(u) + pre(v) − 2·pre(lca) + val(lca). Blelloch also discusses the linked-list version of all-prefix-sums (list ranking), which is the basis of many parallel tree algorithms. [1][8]

N.6 Engineering trade-offs at scale

Pibiri and Venturini benchmark many prefix-sum data structures and find that practical factors — branch-free versus branchy traversal, cache conflicts in the Fenwick tree layout, SIMD for updates and wide tree fan-outs — change which structure wins on modern CPUs; for example, a 64-ary segment tree was their best general-purpose choice for arbitrary 64-bit updates. [23]

P.5 Answer key

Conceptual answers
  1. P[k] means “sum of the first k elements”, so k ranges over 0…n: n+1 values. The slot P[0] = 0 represents the empty prefix and makes ranges that start at index 0 use the same formula (P[R+1] − P[0]). Without it you need a special case, and in Python the unguarded pre[L−1] with L = 0 silently reads the last element.
  2. Addition (inverse: subtraction) and XOR (self-inverse) work. Multiplication works only if no element is zero (otherwise division is undefined) and is numerically risky for floats. Maximum and gcd have no inverse — knowing max(A[0..R]) and max(A[0..L−1]) does not determine max(A[L..R]) — so use a sparse table or segment tree.
  3. Each update costs up to 106 writes: roughly 105 × 5·105 ≈ 5·1010 operations on average — far too slow. A Fenwick tree gives O(log n) ≈ 20 steps per operation: about 4·106 steps total, plus O(n) build.
  4. The window method decides to shrink or grow based on whether the current sum is above or below k, which is only valid when adding elements can never decrease the sum. With negatives, a window that is “too big” might become valid after extending it further. The hash-map method enumerates, for each end position, all start positions implicitly via the equation P[i] = P[j] − k, with no monotonicity assumption.
  5. The top-left block above and to the left of the rectangle is contained in both subtracted strips (S[r1][c2+1] and S[r2+1][c1]), so it was removed twice. Adding S[r1][c1] once restores the correct count (inclusion–exclusion).

from itertools import accumulate
from operator import xor

# 1. Range XOR
def xor_queries(arr, queries):
    X = list(accumulate(arr, xor, initial=0))
    return [X[r + 1] ^ X[l] for l, r in queries]

# 2. Longest subarray with sum k (negatives allowed)
def longest_subarray_sum_k(nums, k):
    first = {0: -1}                 # store the FIRST index of each prefix value
    running = best = 0
    for i, x in enumerate(nums):
        running += x
        if running - k in first:
            best = max(best, i - first[running - k])
        if running not in first:    # never overwrite: earliest index gives longest span
            first[running] = i
    return best

# 3. Best k x k square
def best_square(grid, k):
    R, C = len(grid), len(grid[0])
    S = [[0] * (C + 1) for _ in range(R + 1)]
    for r in range(R):
        for c in range(C):
            S[r + 1][c + 1] = grid[r][c] + S[r][c + 1] + S[r + 1][c] - S[r][c]
    best = None
    for r in range(k, R + 1):
        for c in range(k, C + 1):
            s = S[r][c] - S[r - k][c] - S[r][c - k] + S[r - k][c - k]
            best = s if best is None else max(best, s)
    return best

Complexities: (1) Θ(n + q); (2) Θ(n) expected, O(n) space; (3) Θ(rc) time and space.

Engineering scenario — model answer

Split the data by mutability. Closed hours (immutable) are stored per service as a cumulative array: one int64 running total per second, so any query fully inside history is C[t2+1] − C[t1] in O(1). One year is about 3.15·107 seconds, i.e. ≈252 MB per service at 8 bytes each — so in practice you also keep a coarser cumulative array per minute or hour and only load per-second blocks when needed (two-level prefix sums: whole buckets from the coarse array, partial buckets from the fine one).

Mutable recent window. The current and previous hour (≤ 7,200 seconds) accept writes and late corrections, so keep them in a Fenwick tree: O(log 7200) ≈ 13 steps per update or query. When an hour can no longer change, freeze it: compute its cumulative array in O(3600) and append it, offset by the running total so far.

Query. Split [t1, t2] into the frozen part (two lookups) plus the live part (two Fenwick prefix queries). Integer type: 64-bit signed — a year of per-second counts can exceed 231, and NumPy-style fixed-width arithmetic would wrap silently. [6][7]
