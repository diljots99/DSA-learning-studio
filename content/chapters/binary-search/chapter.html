BFundamental understanding

What is binary search?

Binary search finds a value in a sorted sequence by repeatedly comparing it with the element in the middle of the part that could still contain it, and throwing away the half that cannot. Princeton’s Algorithms text presents it as the reason to keep symbol-table keys in an ordered array: array indexing lets us jump to the middle, which “dramatically” reduces the number of comparisons. [3] CP-Algorithms describes the same idea more generally as “splitting the search interval into two” — the target need not even be an array element, as Section N shows. [5]

Formal definition Let A[0..n−1] be sorted in non-decreasing order and let x be a key. Binary search maintains an interval of indices that must contain x if x occurs in A. At each step it probes the middle index m of the interval, compares A[m] with x, and either stops (A[m] = x) or replaces the interval with the half on the correct side of m. It reports “not found” when the interval becomes empty. In the worst case it uses at most ⌊lg n⌋ + 1 comparisons. [3][4]
Simple English definition Binary search is the “higher or lower?” guessing game played perfectly: always guess the middle of what is still possible, and every answer crosses out half the possibilities.

Why does it exist, and what came before it?

Before binary search, the only general way to look something up was linear (sequential) search: check items one by one, which costs O(n) comparisons — Python’s x in my_list is exactly such a scan. [22] Sorting the data first buys a powerful guarantee: every element to the left of position m is ≤ A[m] and every element to the right is ≥ A[m]. One comparison therefore tells you about half the array at once. Binary search exists to cash in on that guarantee. MIT 6.006 shows that in the comparison model no algorithm can do better than Ω(log n) for searching, so binary search is optimal there. [1][2]

A little history

Ordered tables for lookup are ancient: Knuth’s history of searching (as summarised in the Wikipedia survey) cites a Babylonian tablet from about 200 BCE holding a sorted table. [9][10] The first explicit description of binary search for computers is credited to John Mauchly in the 1946 Moore School Lectures. [9] Getting it right took longer: Jon Bentley wrote that although the first binary search was published in 1946, the first version correct for all values of n did not appear until 1962. [8] Bentley also reported that when he assigned binary search to professional programmers, about ninety percent failed to produce a correct solution. [9] And in 2006 Joshua Bloch showed that the textbook midpoint line mid = (low + high) / 2 — including the one in Java’s own library, which he had written — overflows on arrays of about 230 elements. [8] The idea is simple; the details are where people slip, which is why this chapter spends so long on invariants.

Fundamental principles

  1. Order lets one comparison speak for many elements. If A[m] < x and the array is sorted, then every A[i] with i ≤ m is also < x. [3]
  2. Random access makes the middle cheap. Jumping to index m must be O(1), as in an array; on a linked list, reaching the middle costs O(n) and the advantage disappears. [22]
  3. Halving gives logarithms. An interval of size n can be halved only about log₂ n times before it is empty. [5]
  4. An invariant keeps you honest. State what the interval means (“if x is present, it is inside [lo, hi]”) and make every update preserve that statement. Correctness and termination follow. [5]
  5. Really, you are finding a boundary. Most binary-search problems ask for the first position where a yes/no question flips from “no” to “yes”. That view — a monotone predicate — is what makes binary search a general technique. [11][5]

CThe problem statement

The sorted search problem

ComponentSpecification

Why the naive approach is inefficient

Linear search ignores the order and may look at every element: n comparisons in the worst case and about n/2 on average for a successful search. For a table of 109 keys answering 105 queries, that is up to 1014 comparisons. Binary search answers the same workload with at most 30 × 105 = 3·106. [3][5]

Limitations of alternative approaches

A hash table answers “is x present?” in expected O(1), but it keeps no order, so it cannot answer “what is the largest key ≤ x?” or “how many keys lie between 10 and 20?”. MIT 6.006’s data-structure table records exactly this: hash tables have no efficient find_next, while a sorted array supports it in O(log n). [2] The Python documentation itself notes that bisection is the right tool for range searches and dictionaries for exact lookups. [6] A balanced binary search tree supports ordered queries and fast insertion, but uses extra pointers per key and has poorer memory locality than a flat array.

How binary search improves the solution

It exploits the order that is already there. Each comparison halves the candidates, so the work grows with log n, not n, and the only extra memory is two or three integer indices. The price is paid up front: the data must be sorted (O(n log n) once) and kept sorted, and inserting into a sorted array costs O(n) because elements shift. [2][3][6]

Real-world analogy: the dictionary on your desk ILLUSTRATIVE To find “otter” in a 1 000-page paper dictionary you do not read from page 1. You open near the middle, see “mango”, and know “otter” is in the right half — 500 pages gone in one look. Open the middle of that half, and so on. About ten looks find the page, because 210 = 1024. The method only works because the words are alphabetised (sorted) and you can flip straight to any page (random access). Shuffle the pages, or glue them into a scroll, and you are back to reading from the start.

FInternal working

F.1 Data organisation and memory

Binary search needs nothing but the sorted sequence and a few integers: lo, hi and mid. It never copies or modifies the array, so its auxiliary space is O(1) in the iterative form. [9] In CPython a list is an array of references, so a[mid] is a constant-time address computation followed by one comparison of the referenced objects. [22] Two consequences are easy to miss: (1) the comparison may be expensive (two long strings compare character by character), and (2) slicing — a[mid+1:] — copies elements, which silently turns an O(log n) search into O(n) (see Section L). [22]

F.2 Execution flow

In words, the classic algorithm runs these numbered steps [3][4]:

  1. Set the interval to the whole array: lo = 0, hi = n − 1.
  2. While the interval is non-empty (lo ≤ hi), compute mid = lo + (hi − lo) // 2.
  3. Compare once. If A[mid] == x you are done.
  4. If A[mid] < x, then A[lo..mid] are all < x: discard them with lo = mid + 1.
  5. Otherwise A[mid..hi] are all > x: discard them with hi = mid − 1.
  6. If the loop exits, the interval is empty and x is absent; lo is its insertion point.

F.3 Two templates you must not mix

Almost every binary-search bug comes from mixing two different meanings of hi. Pick one template, and let its invariant dictate every line. [5][7]

Closed [lo, hi] — “find x” lo, hi = 0, n − 1
while lo <= hi:
  lo = mid + 1 or hi = mid − 1
Invariant: if x is present, its index is in [lo, hi]. Empty when lo = hi + 1. Natural when you can stop on equality.
Half-open [lo, hi) — “find a boundary” lo, hi = 0, n
while lo < hi:
  lo = mid + 1 or hi = mid
Invariant: answer index is in [lo, hi], with hi = n meaning “none”. Ends when lo = hi — that is the answer. This is CPython’s bisect_left. [7]

F.5 Inside Python’s bisect

CPython’s Lib/bisect.py implements bisect_left with the half-open template: while lo < hi: mid = (lo + hi) // 2; if a[mid] < x: lo = mid + 1 else: hi = mid, and raises ValueError if lo is negative. At the end of the file it imports a C accelerator, _bisect, which replaces those pure-Python definitions when available. [7] The functions only call __lt__, so any type with a consistent “less than” works; since Python 3.10 they accept a key= function, which is applied to the array elements but not to x. [6] Writing (lo + hi) // 2 is safe in Python because its integers have unlimited precision — there is no overflow to guard against, unlike in Java or C. [21][8]

GMathematical foundation

G.1 Correctness by loop invariant

Invariant (closed template) I: for every index i < lo, A[i] < x; and for every index i > hi, A[i] > x. Equivalently: if x occurs in A, it occurs in A[lo..hi]. [5]
  1. Initialisation. With lo = 0, hi = n−1 there are no indices < lo or > hi, so I holds vacuously.
  2. Maintenance. If A[mid] < x, sortedness gives A[i] ≤ A[mid] < x for all i ≤ mid, so setting lo = mid+1 keeps I. The case A[mid] > x is symmetric with hi = mid−1.
  3. Termination with an answer. If A[mid] = x we return a correct index. If the loop exits, then lo = hi + 1, every index is either < lo or > hi, and by I none holds x — so −1 is correct, and lo is the insertion point.
  4. Progress. Since lo ≤ mid ≤ hi, both updates strictly decrease the non-negative quantity hi − lo + 1, so the loop runs a finite number of times.

The half-open template uses the invariant “A[i] < x for i < lo and A[i] ≥ x for i ≥ hi”; CP-Algorithms phrases the same idea as maintaining A_L ≤ k < A_R across the loop. [5] The proof above is the author’s standard textbook argument, written out for this chapter.

G.2 How many comparisons? The recurrence

Let C(n) be the worst-case number of three-way comparisons on an interval of n elements. One comparison at the middle leaves at most ⌊n/2⌋ elements (the larger side of the remaining n − 1), so

C(0) = 0,    C(n) = 1 + C(⌊n/2⌋)   ⟹   C(n) = ⌊log₂ n⌋ + 1 for n ≥ 1

Unrolling: each halving removes one binary digit of n, and n has ⌊log₂ n⌋ + 1 digits. This matches Princeton’s Proposition B (“no more than lg N + 1 compares”) and the Master Theorem case T(n) = T(n/2) + Θ(1) = Θ(log n). [3][25] The companion code verifies C(n) = ⌊log₂ n⌋ + 1 exhaustively for every n < 300 (Python’s n.bit_length()).

G.3 Why nobody can do better: the decision-tree lower bound

MIT 6.006 states the result as: any decision tree with n nodes has height at least ⌈lg(n+1)⌉ − 1, hence searching among n preprocessed items needs Ω(lg n) comparisons and binary search is optimal in the comparison model. [2][1] Since ⌈log₂(n+1)⌉ = ⌊log₂ n⌋ + 1 for every n ≥ 1, binary search meets the bound exactly, not just asymptotically. Hash tables escape the bound only because they leave the comparison model: they compute an address from the key. [2]

G.4 Average case

For a successful search with every key equally likely, the cost is the average depth of a node in the decision tree. When n = 2^k − 1 the tree is perfect: level d (counting the root as 1) has 2^{d−1} nodes, so

average = (1/n) · Σd=1..k d · 2d−1 = ((k − 1)·2k + 1) / n  ≈  log₂ n − 1

For n = 7: (2·8 + 1)/7 = 17/7 ≈ 2.43 comparisons, versus a worst case of 3. So the average is only about one comparison below the worst case — binary search is Θ(log n) on average too. (This derivation is the author’s; the Wikipedia survey reports the same near-log₂ n behaviour from Knuth.) [9]

G.5 The monotone-predicate view

The “main theorem” of binary search Let p be a predicate on an ordered search space S. Binary search can find the smallest t with p(t) true if and only if p is monotone: p(t) implies p(u) for every u > t. [11]

Searching for x in a sorted array is the special case p(i) = [A[i] ≥ x]; the array’s sortedness is precisely what makes p monotone. CP-Algorithms makes the same generalisation: replace the comparison with “an arbitrary monotonous predicate”. [5] That single observation powers Section M’s “binary search on the answer” problems.

Reasoning behind each entry

  • Find, best case Θ(1): the first probe may hit the target. Worst case Θ(log n): the recurrence of G.2. Both bounds are tight, so we may write Θ(log n) for the worst case: O(log n) from the recurrence and Ω(log n) from the decision tree. [3][2]
  • Average Θ(log n): G.4 — about one comparison less than the worst case. [9]
  • Bounds have no early exit: bisect_left never stops on equality, so it always runs about ⌈log₂(n+1)⌉ iterations — best = worst = Θ(log n). [7]
  • Recursive space: each call adds a stack frame and there are at most ⌊log₂ n⌋ + 1 calls — only about 31 frames for a billion elements, far below Python’s default recursion limit. [26]
  • insort Θ(n): the search is O(log n) but “is dominated by the slow O(n) insertion step”, because list.insert shifts the tail. [6][22] Princeton notes that inserting N keys into an ordered array costs ~N² array accesses in the worst case. [3]
  • Search on the answer: ⌈log₂ R⌉ predicate evaluations, each costing C (often O(n) to scan the input). [5]
Amortized analysis — where it does and does not apply A single search has no amortized component. Amortization appears only in the surrounding structure: if you append keys that arrive in increasing order, insort inserts at the end and list.append’s amortized O(1) applies; for arbitrary keys each insertion is genuinely Θ(n). Sorting once and then answering q queries costs O(n log n + q log n), versus O(qn) for repeated linear search, so the one-off sort pays for itself once the number of queries exceeds roughly log n. [22]

Time–space trade-offs

Binary search is the low-memory end of the searching spectrum: O(1) extra space and no per-key overhead. A hash set spends extra memory (empty slots, stored hashes) to reach expected O(1) lookups but loses order. A balanced BST spends pointer memory to make insertion O(log n). Layout tricks such as the Eytzinger order (Section N) spend a one-off permutation to make each probe more cache-friendly. [2][15]

Theory versus real Python behaviour

  • bisect runs in C (the _bisect accelerator), so it is many times faster per step than a hand-written Python loop; prefer it in production code. [7]
  • With key=, the key function is called on every probed element on every call; for expensive keys the docs recommend searching a precomputed list of keys. [6]
  • For small lists, a linear scan in C (x in lst) can beat a Python-level binary search despite the worse asymptotics — measure before micro-optimising.
  • On very large arrays, each probe of a plain binary search can touch a different cache line, so memory latency, not comparisons, dominates the running time. [15]

I.1 Classic iterative binary search (from scratch)

def binary_search(a: Sequence, target) -> int:
    """Return an index i with a[i] == target, or -1 if target is absent.

    Precondition: a is sorted in non-decreasing order.
    Invariant: if target is in a, its index lies in the closed range [lo, hi].
    """
    lo, hi = 0, len(a) - 1
    while lo <= hi:                      # range [lo, hi] is non-empty
        mid = lo + (hi - lo) // 2        # overflow-safe form (habit from C/Java)
        if a[mid] == target:
            return mid                   # found
        elif a[mid] < target:
            lo = mid + 1                 # target can only be to the right
        else:
            hi = mid - 1                 # target can only be to the left
    return -1                            # range became empty: absent

I.2 Recursive version

def binary_search_rec(a: Sequence, target, lo: int = 0, hi: Optional[int] = None) -> int:
    if hi is None:
        hi = len(a) - 1
    if lo > hi:                          # base case: empty range
        return -1
    mid = lo + (hi - lo) // 2
    if a[mid] == target:
        return mid
    if a[mid] < target:
        return binary_search_rec(a, target, mid + 1, hi)
    return binary_search_rec(a, target, lo, mid - 1)

Same invariant; the interval is passed as parameters instead of being updated in place. Passing indices — never slices like a[mid+1:] — keeps each call O(1). Recursion depth is at most ⌊log₂ n⌋ + 1, so stack usage is O(log n). Stanford’s CS106B uses exactly this recursive shape to introduce binary search. [23]

I.3 Boundary searches (half-open template)

def lower_bound(a: Sequence, x) -> int:
    """First index i with a[i] >= x (len(a) if none). Same as bisect_left."""
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1                 # a[mid] is too small: answer is right of mid
        else:
            hi = mid                     # a[mid] >= x: mid might be the answer
    return lo

def upper_bound(a: Sequence, x) -> int:
    """First index i with a[i] > x (len(a) if none). Same as bisect_right."""
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] <= x:
            lo = mid + 1
        else:
            hi = mid
    return lo

def search_range(a: Sequence, x) -> List[int]:
    """[first, last] index of x in sorted a, or [-1, -1]. (LeetCode 34)"""
    i = lower_bound(a, x)
    if i == len(a) or a[i] != x:
        return [-1, -1]
    return [i, upper_bound(a, x) - 1]

def count_occurrences(a: Sequence, x) -> int:
    return upper_bound(a, x) - lower_bound(a, x)

These mirror CPython’s own bisect_left/bisect_right line for line. [7] Note hi = mid (not mid − 1): when a[mid] ≥ x, mid itself may be the answer, so it must stay inside [lo, hi]. Progress is still guaranteed because mid < hi whenever lo < hi.

I.4 The general tool: first True of a monotone predicate

def first_true(lo: int, hi: int, pred: Callable[[int], bool]) -> int:
    """Smallest integer t in [lo, hi) with pred(t) True, or hi if none.

    Requires pred to be monotone: False ... False True ... True.
    """
    while lo < hi:
        mid = (lo + hi) // 2
        if pred(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

Every boundary search is first_true with a particular predicate: lower_bound(a, x) == first_true(0, len(a), lambda i: a[i] >= x). This is Topcoder’s “main theorem” turned into code. [11][5]

I.7 Edge cases and error handling

def safe_binary_search(a, target, *, check_sorted: bool = False) -> int:
    if not hasattr(a, "__getitem__") or not hasattr(a, "__len__"):
        raise TypeError("binary search needs a random-access sequence (list, tuple, range, array)")
    if check_sorted and any(a[i] > a[i + 1] for i in range(len(a) - 1)):
        raise ValueError("input is not sorted in non-decreasing order")
    return binary_search(a, target)
  • Empty input returns −1 (classic) or 0 (bounds) without touching the list.
  • Sortedness is a precondition. Checking it costs O(n) and would destroy the point of an O(log n) search, so it is opt-in (check_sorted=True) — useful in tests, not in hot paths. Python’s bisect likewise trusts the caller. [6]
  • Non-indexable input (a set, a generator) raises TypeError: binary search needs random access.
  • Mixed types (e.g. [1, "a"]) raise TypeError from < in Python 3 — a feature, not a bug.
  • Floating-point keys: NaN compares false with everything and breaks the ordering; filter it out before sorting.

When should binary search be avoided?

  • The data is unsorted and you will search only once or twice. Sorting costs Θ(n log n); one linear scan costs Θ(n).
  • Inserts and deletes are as frequent as lookups. Each insert into a sorted array is O(n). [6]
  • No random access (linked lists, streams). Use a tree, skip list or a different index.
  • Only exact-match lookups on hashable keys: a dict/set is simpler and faster; the bisect documentation says the same. [6]
  • The predicate is not monotone. Binary search silently returns garbage; prove monotonicity first. [11]

LCommon mistakes & misconceptions

Bentley’s observation that most professional programmers wrote an incorrect binary search [9] is a good reason to study the failure modes one by one. Lab 6 lets you run four of them.

1. Loop condition that does not match the interval (Bug A)

✘ Wrong
lo, hi = 0, len(a) - 1      # closed interval
while lo < hi:               # stops when one candidate is left
    ...
return -1                   # never checks a[lo]!
# binary_search([1, 3], 3) returns -1
✔ Right
lo, hi = 0, len(a) - 1      # closed interval
while lo <= hi:              # non-empty while lo <= hi
    ...
return -1

2. Not making progress: lo = mid (Bug B)

✘ Wrong
while lo < hi:
    mid = (lo + hi) // 2     # lower middle
    if a[mid] <= x:
        lo = mid             # when hi == lo + 1, mid == lo
    else:                    # → nothing changes: infinite loop
        hi = mid - 1
✔ Right (“last index with a[i] ≤ x”)
while lo < hi:
    mid = (lo + hi + 1) // 2 # UPPER middle when lo = mid
    if a[mid] <= x:
        lo = mid
    else:
        hi = mid - 1
# or simply: upper_bound(a, x) - 1

Rule: if a branch sets lo = mid, round mid up; if it sets hi = mid, round down. Otherwise a two-element interval never shrinks.

3. Wrong initial hi (Bug C)

hi = len(a) belongs to the half-open template. Combined with while lo <= hi it eventually probes a[len(a)] and raises IndexError when the target exceeds every element.

4. Midpoint overflow in fixed-width languages (Bug D)

✘ Wrong (Java/C/C++)
int mid = (low + high) / 2;  // low + high may exceed 2^31 - 1
✔ Right
int mid = low + (high - low) / 2;
int mid = (low + high) >>> 1;   // Java unsigned shift

Bloch reported that this exact line broke Java’s Arrays.binarySearch once arrays reached about 230 elements; the sum overflows to a negative number and the program crashes with an index exception. [8] Python is immune because its integers have unlimited precision, [21] and CPython’s own bisect uses (lo + hi) // 2. [7]

5. Slicing in recursion

✘ Wrong
def bs(a, x):
    if not a: return False
    m = len(a) // 2
    if a[m] == x: return True
    return bs(a[m+1:], x) if a[m] < x else bs(a[:m], x)
# each slice copies → O(n) total time and space,
# and the original index is lost
✔ Right
# pass indices, not slices
def bs(a, x, lo=0, hi=None):
    if hi is None: hi = len(a) - 1
    if lo > hi: return -1
    m = (lo + hi) // 2
    ...

Python slicing a list of length k costs O(k), so the copies sum to n/2 + n/4 + … = O(n). [22]

6. Assuming the classic search returns the first occurrence

On [2, 2, 2, 2, 2] the classic loop returns index 2 — the first probe. If the question is “first” or “last” occurrence, use bisect_left / bisect_right − 1 (LeetCode 34). [6]

7. Searching unsorted data, or sorting for a single query

Binary search on unsorted input is not “slower” — it is wrong: it can miss elements that are present. And sort + one search is Θ(n log n), worse than one Θ(n) scan. “Binary search is O(log n)” is true only after the data is sorted.

8. Complexity misconceptions

  • “O(log n) on a linked list”: comparisons are O(log n) but reaching each middle node is a walk, so total time is O(n).
  • “Log base matters”: log₂ n and log₁₀ n differ by a constant factor, so both are O(log n); the base matters only for exact comparison counts.
  • “Ternary search is faster because it cuts into thirds”: it makes two comparisons per step, about 2 log₃ n ≈ 1.26 log₂ n comparisons — more than binary search. (Author’s arithmetic: 2/ log₂ 3 ≈ 1.26.)

9. Answer-space bounds that are not valid

In Koko (Lab 4), starting the speed range at 0 causes division by zero, and an upper end that is not feasible returns a wrong answer. Pick lo = smallest conceivable answer and hi = a value known to satisfy the predicate (max(piles)).

10. Floating-point loops that never end

✘ Risky
while hi - lo > 1e-12:      # may spin forever when
    mid = (lo + hi) / 2     # lo and hi are adjacent floats
    ...
✔ Robust
for _ in range(100):        # 2**-100 shrink: plenty
    mid = (lo + hi) / 2
    ...

11. Interview mistakes

  • Coding before saying what lo and hi mean. State the invariant aloud first.
  • Not testing n = 0, 1, 2, target below the minimum, above the maximum, and duplicates.
  • Reaching for binary search on a non-monotone condition (e.g. searching a rotated array with the plain algorithm).
  • Forgetting to mention that Python’s bisect exists — interviewers usually accept it once you can explain it.

def search_rotated(nums: Sequence[int], target: int) -> int:
    """LeetCode 33 — distinct values, sorted then rotated."""
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:                    # left half [lo..mid] is sorted
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:                                        # right half [mid..hi] is sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1

Each step still discards half: O(log n) time, O(1) space. With duplicates (LeetCode 81) the case nums[lo] == nums[mid] == nums[hi] cannot be decided, and the worst case degrades to O(n).

6. Find Peak Element MEDIUM

def find_peak(nums: Sequence[int]) -> int:
    """LeetCode 162 — index of any element greater than its neighbours."""
    lo, hi = 0, len(nums) - 1

7. Median of Two Sorted Arrays HARD

LeetCode 4 — median of two sorted arrays in O(log(m + n)).

Hint 1Choose how many elements i the left half takes from the shorter array A; then j = half − i come from B.
Hint 2The cut is correct iff A[i−1] ≤ B[j] and B[j−1] ≤ A[i]. If A[i−1] > B[j], i is too big — that is the monotone predicate.
Solution & complexity 
def median_two_sorted(A: Sequence[int], B: Sequence[int]) -> float:
    """LeetCode 4 — O(log(min(m, n))) partition search."""
    if len(A) > len(B):
        A, B = B, A
    m, n = len(A), len(B)
    if m + n == 0:
        raise ValueError("both arrays are empty")
    half = (m + n + 1) // 2
    lo, hi = 0, m
    NEG, POS = float("-inf"), float("inf")
    while lo <= hi:
        i = (lo + hi) // 2               # elements taken from A
        j = half - i                     # elements taken from B
        a_left = A[i - 1] if i > 0 else NEG
        a_right = A[i] if i < m else POS
        b_left = B[j - 1] if j > 0 else NEG
        b_right = B[j] if j < n else POS
        if a_left <= b_right and b_left <= a_right:
            if (m + n) % 2:
                return float(max(a_left, b_left))
            return (max(a_left, b_left) + min(a_right, b_right)) / 2
        if a_left > b_right:
            hi = i - 1
        else:
            lo = i + 1
    raise AssertionError("unreachable for sorted inputs")

Binary search over i ∈ [0, min(m, n)]: O(log min(m, n)) time, O(1) space. Tested against brute-force merging on 4 000 random inputs.

NAdvanced concepts

N.1 Exponential (galloping) search — when n is unknown or the answer is near the front

Probe indices 1, 2, 4, 8, … until you overshoot the target, then binary search inside the last bracket. Bentley and Yao introduced this family for searching unbounded ordered tables and showed it is almost optimal. [12] If the answer sits at position i, the cost is O(log i) rather than O(log n).

def exponential_search(a: Sequence, target) -> int:
    """Galloping search: find a bracket [bound/2, bound] then binary search it."""
    if not a:
        return -1
    bound = 1
    while bound < len(a) and a[bound] < target:
        bound *= 2
    lo, hi = bound // 2, min(bound, len(a) - 1)
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

N.2 Interpolation search — guessing smarter than the middle

Instead of the middle, probe where the key should be if values are evenly spread: pos = lo + (x − A[lo]) · (hi − lo) / (A[hi] − A[lo]). Perl, Itai and Avni proved an average of about log log n probes for uniformly distributed keys, [13] but the worst case for skewed data is O(n), and the extra arithmetic often makes it no faster than binary search in practice. [14]

N.3 Bisection on real numbers

For a continuous monotone function, binary search on an interval approximates the crossing point to within ±δ in O(log((R − L)/δ)) iterations. [5] Using a fixed iteration count avoids floating-point non-termination:

def sqrt_real(x: float, eps: float = 1e-9) -> float:
    """Bisection on real numbers: 100 halvings shrink any interval by 2**-100."""
    if x < 0:
        raise ValueError("x must be non-negative")
    lo, hi = 0.0, max(1.0, x)
    for _ in range(100):
        mid = (lo + hi) / 2
        if mid * mid < x:
            lo = mid
        else:
            hi = mid
    return hi

Output: sqrt_real(2) = 1.414213562373.

N.4 Making each probe cheaper: memory layout

Khuong and Morin benchmarked layouts for comparison-based searching and concluded that for small arrays a well-implemented binary search on sorted order is best, while for larger arrays the Eytzinger (breadth-first, heap-like) layout with branch-free code and prefetching performed best. [15] In the Eytzinger layout the root is at index 1 and the children of k are at 2k and 2k + 1, so the first few levels share cache lines. The Wikipedia survey also notes that plain binary search on large power-of-two arrays can thrash caches and TLBs. [9]

N.5 Many searches at once

  • Fractional cascading (Chazelle & Guibas, 1986) speeds up searching for the same key in k related sorted lists from O(k log n) to O(log n + k) by threading pointers between them. [24][9]
  • Parallel binary search answers many independent “first time the predicate becomes true” queries together, sweeping the shared process once per halving round. [5]

N.6 Variants with history

  • Deferred equality test. Bottenbruch’s 1962 ALGOL version tested equality only at the end, using one comparison per iteration at the cost of about one extra iteration — the ancestor of today’s bisect_left. [9]
  • Uniform binary search stores the sequence of step sizes in a precomputed table instead of computing midpoints. [9][10]
  • Noisy binary search tolerates comparisons that sometimes lie, at the price of extra comparisons governed by an entropy bound. [9]

Binary Search
Sorted + random access → compare with the middle → throw away half
What is it?

Find x in a sorted array by checking the middle of the part that could still hold it, then keeping only the correct half.

mid = lo + (hi − lo) // 2

Needs: sorted order + O(1) indexing (array, not linked list).

The invariant

“If x is in A, it is inside [lo, hi].”

A[mid] < x → lo = mid + 1
A[mid] > x → hi = mid − 1

Loop while lo ≤ hi. Exit ⇒ absent, and lo = insertion point.

Traps
  • lo < hi with closed [lo, hi] → misses last one
  • lo = mid with lower mid → infinite loop
  • (lo+hi)/2 overflow in Java/C
  • slicing a[mid:] → O(n)

3 comparisons for 10 items → index 5

Boundaries (duplicates)
bisect_left = first a[i] ≥ x
bisect_right = first a[i] > x

count(x) = right − left · last = right − 1

1 · Formal definition

  • Given sorted A[0..n−1] and key x, keep an interval that must contain x; compare x with A[mid]; keep one half; stop on match or empty interval.

2 · Core concept

  • One comparison with the middle eliminates half the candidates because of sortedness.
  • Really: find the first True of a monotone predicate.

3 · Key properties

  • Preconditions: sorted, random access.
  • Worst case ⌊log₂ n⌋ + 1 = ⌈log₂(n+1)⌉ comparisons — optimal in the comparison model (decision tree).
  • Iterative space O(1); recursive O(log n).

4 · Two templates

  • Closed: hi = n−1, while lo <= hi, lo = mid+1 / hi = mid−1.
  • Half-open: hi = n, while lo < hi, lo = mid+1 / hi = mid → returns boundary.
  • lo = mid ⇒ use upper mid (lo+hi+1)//2.

5 · Important operations

  • find · lower bound · upper bound · count = ub − lb · predecessor = A[ub(x)−1] · successor = A[lb(x)] · range count = ub(R) − lb(L).

6 · Python syntax

  • i = bisect_left(a, x); found = i < len(a) and a[i] == x
  • insort(a, x) keeps a sorted (O(n)).

7 · Applications

  • Sorted indexes, git bisect, LevelDB blocks, kernel bsearch, price/grade bands, capacity planning by answer search, numeric bisection.

Practical engineering scenario

ILLUSTRATIVE An analytics service keeps 50 million event timestamps (64-bit integers) in memory, appended in arrival order, which is almost sorted (events can arrive up to 5 seconds late). Dashboards ask “how many events between time t₁ and t₂?” thousands of times per second. A teammate proposes bisect on the raw list. What goes wrong, and what design would you propose?

Answers

Conceptual answers
  1. Each probe must reach node mid by following pointers. The walks have lengths about n/2, n/4, … (or worse, restarting from the head), summing to Θ(n). Binary search’s time bound needs O(1) random access.
  2. Invariant: every index < lo holds a value < x, every index ≥ hi holds a value ≥ x. When a[mid] ≥ x, mid itself satisfies the “≥ x” side and might be the first such index, so it must stay as the new exclusive-boundary candidate hi = mid; mid − 1 could skip the answer. Progress holds because mid < hi while lo < hi.
  3. Each comparison leaves at most ⌊m/2⌋ of m candidates, so C(n) = 1 + C(⌊n/2⌋) = number of binary digits of n. Any comparison algorithm is a binary decision tree that needs at least n distinct “found at i” outcomes (plus the gaps), so its height is ≥ ⌈log₂(n+1)⌉ − 1 edges, i.e. some input needs ⌈log₂(n+1)⌉ = ⌊log₂ n⌋ + 1 comparisons. [2]
  4. Pure membership → hash set: expected O(1), easy updates. Range counting needs order → sorted list with bisect_right(R) − bisect_left(L) (or a balanced tree if blocks change often).
  5. It must be monotone: once True, True for every larger value. Counter-example: p(t) = (t is even) on integers — F T F T…, so “first True” cannot be found by halving.

Coding answers 
from bisect import bisect_left, bisect_right

def range_count(a, L, R):                   # 1. O(log n) per query
    return max(0, bisect_right(a, R) - bisect_left(a, L))

def find_min_rotated(nums: Sequence[int]) -> int:
    """LeetCode 153 — minimum of a rotated sorted array with distinct values."""
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:
            lo = mid + 1          # minimum is strictly right of mid
        else:
            hi = mid              # mid could be the minimum
    return nums[lo]

def smallest_divisor(nums: Sequence[int], threshold: int) -> int:
    """LeetCode 1283 — smallest d with sum(ceil(x / d)) <= threshold."""
    return first_true(1, max(nums) + 1,
                      lambda d: sum((x + d - 1) // d for x in nums) <= threshold)

(2) Compare nums[mid] with nums[hi], not nums[lo]: if nums[mid] > nums[hi] the rotation point (the minimum) is strictly to the right. O(log n). (3) The sum of ceilings never increases as d grows, so the predicate is monotone on [1, max(nums)]; O(n log max). Example: smallest_divisor([1, 2, 5, 9], 6) = 5. All three were tested against brute force in the companion module.

Engineering scenario answer

What goes wrong: the list is not sorted, so bisect may return counts that are silently wrong near late events — the sortedness precondition is violated, and bisect does not check it. [6] Calling insort for each late event would keep it sorted but costs O(n) per insert on a 50-million-element list. [6]

A better design: keep an immutable sorted array of “sealed” events older than, say, 10 seconds (no event can still arrive for that range), plus a small buffer for the most recent window. Every second, sort the buffer’s sealed part (small) and append it — appends to the end keep the big array sorted cheaply. Range queries become bisect_right(t₂) − bisect_left(t₁) on the sealed array (O(log n), about 26 comparisons for 5·107) plus a scan of the small buffer. This is the same “immutable sorted runs + small mutable buffer” idea that LSM-tree storage engines such as LevelDB use, where each sorted block is searched by binary search. [17] If the hot path is in Python, use a typed array (e.g. NumPy’s searchsorted) to avoid per-object comparisons.
