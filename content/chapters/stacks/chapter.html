BFundamental understanding

What is a stack?

Picture a spring-loaded pile of plates in a cafeteria. You can only put a clean plate on top, and you can only take the top plate. The plate you put down last is the first one taken. A stack is a collection that enforces exactly this discipline. Sedgewick and Wayne define it as a collection “based on the last-in-first-out (LIFO) policy”, and CLRS define it by its delete operation: the element removed is always the one most recently inserted. [1][2]

Formal definition A stack is an abstract data type (ADT) holding a finite sequence S = ⟨s1, s2, …, sk⟩, where sk is the top, with the operations
• push(x): S ← ⟨s1, …, sk, x⟩;
• pop(): if k = 0 signal underflow; otherwise return sk and set S ← ⟨s1, …, sk−1⟩;
• peek() / top(): return sk without removing it; is_empty(): test k = 0; size(): return k.
The defining axiom is pop(push(S, x)) = (S, x): a pop undoes the most recent push. [2][19]
Simple English definition A stack is a pile where you only ever touch the top. Put things on the top (push), take things off the top (pop), or look at the top (peek). Whatever went in last comes out first.

Two words describe the error states. Popping or peeking an empty stack is underflow; pushing onto a stack that has a fixed maximum size and is already full is overflow. [19][2] A stack backed by a growable array or a linked list never overflows in the ADT sense — it simply asks for more memory — but the call stack of a running program does have a fixed size, which is where the famous “stack overflow” error comes from (Section F.5). [20]

An abstract data type, not a memory layout

“Stack” names a behaviour, not a storage scheme. Any structure that can add and remove at one end in constant time can implement it: an array whose last used slot is the top, or a linked list whose head node is the top. Both are standard textbook implementations. [1][2] In Python, the built-in list already behaves as a stack through append() and argument-less pop(), which the official tutorial describes as using a list as a stack. [4]

Why does this concept exist?

Many computations are nested: a function calls a function that calls a function; a bracket opens inside another bracket; an HTML tag contains other tags; an edit is undone after a later edit was undone. Nested structure always closes in the reverse order it opened. A stack is the data structure whose removal order is the reverse of its insertion order, so it is the natural memory for “what am I in the middle of, and what do I return to next?”. That is why stacks appear in compilers, interpreters, processors and operating systems. [20][15]

A little history

Alan Turing used the terms “bury” and “unbury” for calling and returning from subroutines in his 1946 design for the ACE computer. Klaus Samelson and Friedrich L. Bauer developed the stack principle (German Kellerprinzip, “cellar principle”) for translating arithmetic formulas, filed a patent on it in 1957, and Bauer received the IEEE Computer Pioneer Award in 1988 for the invention of the stack principle. [19] In 1961 Edsger Dijkstra described the shunting-yard algorithm, which uses an operator stack to convert ordinary infix formulas into postfix order for the ALGOL 60 compiler. [21][18] Today stacks are built into hardware: the x86 instruction set has push, pop, call and ret instructions that operate on a stack in memory. [14]

Fundamental principles

  1. Restricted access is a feature. By forbidding access to anything but the top, a stack can make every operation O(1) and makes programs easier to reason about: no index bookkeeping, no searching. [2]
  2. Reversal. Pushing a sequence and popping it all gives the sequence back reversed. Every stack algorithm exploits this: matching the most recently opened bracket, returning to the most recent caller, undoing the most recent edit.
  3. Deferred work. A stack stores work you have started but cannot finish yet (an open bracket waiting for its partner, a caller waiting for a return value, an operator waiting for its right operand). The top is always the most urgent pending item. [17]

CThe problem statement

The “most recent unfinished item” problem

Stacks solve a family of problems rather than one. A representative member, used throughout this chapter, is bracket matching:

ComponentSpecification
InputA string s of length n over the characters ( ) [ ] { } (and possibly others to ignore).
OutputTrue if every closing bracket closes the most recently opened, still-unclosed bracket of the same type, and no bracket is left open; otherwise False.
Typical constraintsLeetCode 20 “Valid Parentheses” uses 1 ≤ n ≤ 104; an O(n) single pass is expected.
Key observation“Most recently opened, still unclosed” is precisely the top of a stack of open brackets.

Why the naive approach is inefficient

A natural first idea is to repeatedly find and delete an adjacent matching pair such as () or [] until nothing changes. Each scan is O(n), each scan may remove only one pair, and building the shortened string costs another O(n); for an input such as ((((…)))) that is n/2 rounds, so Θ(n2) work. Counting brackets with a single integer is O(n) but wrong once there are several bracket types: ([)] has balanced counts for both types yet is not properly nested. (Our own worked example; both claims are checked by the lab in Section E.)

Limitations of other approaches

A plain array with an index lets you reach any element, but then you must manage that index yourself and nothing stops code from reading the wrong slot. A queue removes the oldest item, which is the wrong order for nesting: the bracket that must close first is the newest one. A recursive-descent parser does work, but only because recursion uses the call stack implicitly — which means it is still a stack, with a hard depth limit (Python’s default recursion limit is 1000 frames). [8]

How a stack improves the solution

Scan once. Push every opening bracket. On a closing bracket, pop and check that the popped opener matches; at the end, require the stack to be empty. Every character is pushed at most once and popped at most once, so the algorithm is Θ(n) time and O(n) space in the worst case (all openers). The same skeleton — push what is unfinished, pop when it is finished — evaluates expressions, converts infix to postfix, and drives depth-first search. [17][24]

Real-world analogy: the stack of trays and the pile of open tabs Imagine reading a document that links to a definition, which links to an example, which links to a footnote. You keep each page open as you go deeper. When you finish the footnote you close it and land back on the example, then the definition, then the document — the reverse of the order you opened them. Your mental “where was I?” list is a stack: open = push, finish = pop, and the page you return to is always the top. (Illustrative analogy.)

FInternal working



F.1 Memory representation of an array-backed stack


An array-backed stack keeps two pieces of state: a block of slots data and a count n. Items occupy data[0..n−1] with the bottom at index 0, so the top is data[n−1] and the next push writes data[n]. Keeping the top at the end of the array is essential: adding or removing at the end moves nothing, whereas adding at the front would shift every element. Python’s documentation states the consequence for lists directly — append is O(1) amortised and pop(k) costs O(n−k), so pop() from the end is O(1) while pop(0) is O(n). [6][4]


In CPython a list is exactly this structure: a contiguous array of pointers to objects, plus a size and an allocated capacity. list.append is therefore a stack push and list.pop() a stack pop. [10][4]

    3. 

  3. peek(): if n == 0, raise; return data[n−1]. Nothing changes.

[1] Clearing the popped slot matters in garbage-collected languages: if the array still points at a popped object, that object cannot be reclaimed even though the program can no longer reach it through the stack (Java programmers call this loitering).





F.3 What CPython actually does


CPython does not double. Its list_resize over-allocates by about one eighth of the requested size plus a small constant, rounded to a multiple of 4; the source comment gives the growth pattern “0, 4, 8, 16, 24, 32, 40, 52, 64, 76, …”. [10] Any constant-factor growth (here about 1.125×) still gives amortised O(1) appends — only the constant changes. [2] You can watch it yourself: running sys.getsizeof after each append on CPython 3.11 shows capacity jumps at lengths 1, 5, 9 and 17, to 4, 8, 16 and 24 slots — matching the comment. (Measured by us.)



F.4 Execution flow of push and pop (linked list)


    

  1. push(x): head = Node(x, head) — the new node’s next is the old head, then the head moves to the new node.
    2. 

  2. pop(): if head is None, raise; node = head; head = node.next; return node.value.
    3. 



Sedgewick and Wayne’s linked-list Stack implements push and pop by inserting and removing at the beginning of the list, exactly as above. [1] No step depends on the number of nodes, so both are Θ(1) in the worst case. The price is one extra pointer per item and an allocation for every push. [2]



F.5 The call stack: the stack you use without noticing


Every running program has a call stack. When a function is called, a stack frame is pushed holding its return address, parameters and local variables; when it returns, the frame is popped and execution resumes at the saved return address. [20] The operating-systems textbook OSTEP describes the stack as the part of a process’s address space used “to keep track of where it is in the function call chain” and to hold local variables, parameters and return values. [15] On x86, call pushes the return address and the stack grows toward lower addresses. [14]





Interpreters use stacks too. CPython compiles Python to bytecode that operates on a value stack — the dis documentation calls it STACK and says its top “corresponds to STACK[-1]”. [9] Every Java Virtual Machine frame “contains a last-in-first-out (LIFO) stack known as its operand stack”, and WebAssembly instructions likewise “interact with an implicit stack”. [12][13]

GMathematical foundation



G.1 The LIFO axioms


A stack is fully specified by equations relating its operations (an algebraic specification): for every stack S and item x, top(push(S, x)) = x, pop(push(S, x)) = S, isEmpty(new()) = true and isEmpty(push(S, x)) = false; top(new()) and pop(new()) are errors (underflow). Any implementation satisfying these equations is a correct stack. [19]



G.2 Invariant for the array implementation


Representation invariant0 ≤ n ≤ capacity; the stack’s contents bottom→top are exactly data[0], …, data[n−1]; and every slot data[i] with i ≥ n holds None. With shrinking, also n ≥ capacity/4 whenever n > 0.


Proof sketch. The empty constructor establishes it. push only writes slot n (which is free, after growing if needed) then increments n, so the prefix property and the “free slots are None” property both hold afterwards. pop decrements n, reads the old top and sets it to None, restoring both properties. Resizing copies exactly the prefix. Hence each method preserves the invariant, and the axioms of G.1 follow from it.



G.3 Amortised analysis of the doubling array


Count one unit for each element write, including copies. Starting from capacity 1, the i-th push copies i − 1 items when i − 1 is a power of two, and otherwise copies nothing. For n pushes:


T(n) = n + Σj=0⌊log₂(n−1)⌋ 2j  <  n + 2n = 3n   ⟹   T(n)/n < 3 = O(1) amortised


This is the aggregate method. The accounting method gives the same bound: charge each push 3 units — 1 pays for its own write and 2 are saved; when a full array of size m doubles, the m/2 items pushed since the last resize have saved m units, exactly enough to copy all m items. CLRS present both methods, including this dynamic-table example. [2][3]


Why shrink at a quarter, not a half?If the array halved as soon as it became half full, then at n = capacity/2 the sequence push, pop, push, pop, … would grow and shrink on every operation, each costing Θ(n) — Θ(n) per operation forever. Halving only at one-quarter leaves the new array half full, so at least capacity/4 operations must happen before the next resize, and the amortised cost stays O(1). This is exactly the policy of ResizingArrayStack, and CLRS analyse the same contraction rule for dynamic tables. [1][2]


Growth by a constant amount (say +10 slots) is not enough: then a resize happens every 10 pushes and copies Θ(n) items, so n pushes cost Θ(n2). Lab 6 below lets you compare the two policies.



G.4 The “pushed once, popped once” argument


Many stack algorithms have a loop like while stack and condition: stack.pop() inside a for loop, which looks quadratic. It is not: each element is pushed exactly once, so it can be popped at most once, so the total number of pops over the entire run is at most n. Summing, the whole algorithm does O(n) pushes + O(n) pops + O(n) loop tests. CLRS use the same argument for a stack with a MULTIPOP(k) operation: any sequence of n push/pop/multipop operations costs O(n), so O(1) amortised each, even though one multipop can cost Θ(n). [2] The potential function is simply Φ =  number of items on the stack. [2]



G.5 Correctness of bracket matching


Define a string to be balanced if it is empty, or XY for balanced X, Y, or (X) / [X] / {X} for balanced X. Invariant of the checker: after reading a prefix p, the stack holds, bottom to top, exactly the opening brackets of p that are not yet closed, in the order they were opened. A closing bracket is legal iff it matches the latest unclosed opener — the top — so the pop-and-compare test is both necessary and sufficient; and the whole string is balanced iff no opener remains, i.e. the stack ends empty.



G.6 How many orders can a stack produce?


Push the numbers 1, 2, …, n in order, popping whenever you like and writing down each popped value. Not every permutation is reachable — with n = 3 you cannot output 3 1 2. The number of reachable output orders is the Catalan number Cn = (2n choose n)/(n+1) (1, 2, 5, 14, 42, …), because a valid push/pop sequence is exactly a balanced bracket string of n pairs. This question was posed by Knuth in 1968, and the related stack-sortable permutations are counted by the same numbers. [23]

Reasoning behind each entry


Array push/pop. Without a resize, a push or pop is one write and one counter update: Θ(1). A resize copies all n items, so the worst single operation is Θ(n) — that is a true worst case, which matters for latency-sensitive code. Averaged over any sequence of operations the cost is O(1) (Section G.3). This is why Python documents list.append as amortised O(1), noting that an individual operation may occasionally be O(n) when storage is resized. [6][2]


Linked-list push/pop. A constant number of pointer assignments and one allocation: Θ(1) in the worst case (assuming allocation is O(1)). [2]


Big-O, Ω and Θ here. Every stack operation must do at least a constant amount of work, so each is Ω(1); combined with the O(1) bounds they are Θ(1) (amortised for arrays). Stack-based scanning algorithms must read all n inputs (Ω(n)) and do O(n) work by the pushed-once argument, hence Θ(n).


Recurrence view of recursion. A recursive call stack of depth d uses Θ(d) space. For fact(n), T(n) = T(n−1) + Θ(1) gives Θ(n) time and Θ(n) stack space; naive fib(n) takes exponential time but its stack depth is only n, because at any moment only one root-to-leaf path of the recursion tree is on the stack (try Lab 5).

Time–space trade-offs


A doubling array may hold up to twice as many slots as items when growing (and up to four times after shrinks, with the quarter rule), but every slot is just a reference and the slots are contiguous, which is cache-friendly. A linked list uses exactly n nodes but each node carries a pointer plus allocator and object overhead, and nodes are scattered in memory. In practice array-backed stacks are usually faster; linked stacks win when you need a hard O(1) worst case per operation, or when many stacks share structure (persistent stacks, Section N). [1]

I.1 Array-backed stack from scratch


Python’s list already resizes itself, so to see the mechanism we manage a fixed block of slots manually and never call append on it.


class ArrayStack:
    """LIFO stack on a manually resized array (doubling / quarter-full halving)."""

    def __init__(self, capacity=1):
        self._data = [None] * capacity   # fixed block of slots
        self._n = 0                      # number of items; top is _data[_n - 1]

    def __len__(self):
        return self._n

    def is_empty(self):
        return self._n == 0

    def _resize(self, capacity):
        new = [None] * capacity          # allocate a new block...
        for i in range(self._n):         # ...and copy the n live items: Θ(n)
            new[i] = self._data[i]
        self._data = new

    def push(self, item):
        if self._n == len(self._data):   # full -> double
            self._resize(2 * len(self._data))
        self._data[self._n] = item
        self._n += 1

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from empty stack")      # underflow
        self._n -= 1
        item = self._data[self._n]
        self._data[self._n] = None       # avoid loitering: drop the reference
        if 0 < self._n <= len(self._data) // 4:            # quarter full -> halve
            self._resize(len(self._data) // 2)
        return item

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from empty stack")
        return self._data[self._n - 1]

    def capacity(self):
        return len(self._data)

    def __repr__(self):
        return f"ArrayStack({self._data[:self._n]}, cap={len(self._data)})"



Line-by-line notes


    

  • self._data = [None] * capacity — a block of slots, standing in for a raw array; self._n is both the size and the index of the next free slot.
    • 

  • _resize — the only Θ(n) code path: allocate, copy the live prefix, swap the reference.
    • 

  • push — grow before writing when full, then write slot n and increment.
    • 

  • pop — check for underflow first, decrement, read, clear the slot, then maybe shrink. The 0 < n guard keeps the capacity ≥ 1.
    • 

  • Errors use IndexError, the same exception list.pop() raises on an empty list, so the class is a drop-in replacement.
    •

I.2 Linked-list stack from scratch


class _Node:
    __slots__ = ("value", "next")        # no per-instance __dict__: smaller nodes

    def __init__(self, value, next=None):
        self.value = value
        self.next = next


class LinkedStack:
    """LIFO stack on a singly linked list; the head node is the top."""

    def __init__(self):
        self._head = None
        self._n = 0

    def __len__(self):
        return self._n

    def is_empty(self):
        return self._head is None

    def push(self, item):
        self._head = _Node(item, self._head)   # new node points at old top
        self._n += 1

    def pop(self):
        if self._head is None:
            raise IndexError("pop from empty stack")
        node = self._head
        self._head = node.next                # unlink the old top
        self._n -= 1
        return node.value

    def peek(self):
        if self._head is None:
            raise IndexError("peek from empty stack")
        return self._head.value

    def __iter__(self):                       # top -> bottom
        node = self._head
        while node:
            yield node.value
            node = node.next

    def __repr__(self):
        return "top -> " + " -> ".join(map(str, self)) + " -> None"


ls = LinkedStack()
for x in "ABC":
    ls.push(x)
print(ls)                    # top -> C -> B -> A -> None
print(ls.pop(), ls.peek())   # C B


_Node(item, self._head) evaluates self._head before the assignment, so the new node captures the old top and the pointer update is safe in one line. __slots__ is a Python-specific memory optimisation; it removes the per-object attribute dictionary.

I.5 Min-stack: O(1) minimum


Store, next to each item, the minimum of the stack up to and including that item. Popping then restores the previous minimum automatically. CP-Algorithms describes exactly this pair-storing technique. [16]


class MinStack:
    def __init__(self):
        self._s = []                     # (value, minimum of stack up to here)

    def push(self, x):
        m = x if not self._s else min(x, self._s[-1][1])
        self._s.append((x, m))

    def pop(self):
        return self._s.pop()[0]

    def top(self):
        return self._s[-1][0]

    def get_min(self):
        return self._s[-1][1]

I.6 Expressions: shunting-yard and postfix evaluation


Postfix (reverse Polish) notation puts each operator after its operands — 3 4 2 * + means 3 + 4 × 2 — and needs no parentheses. It is evaluated with one operand stack: push numbers; on an operator pop two operands, apply, push the result. [1] Dijkstra’s shunting-yard algorithm converts infix to postfix with an operator stack, popping operators of higher (or equal, for left-associative operators) precedence before pushing a new one; it runs in O(n). [21][17]


import operator

OPS = {"+": operator.add, "-": operator.sub, "*": operator.mul,
       "/": lambda a, b: int(a / b), "^": operator.pow}    # / truncates toward 0
PREC = {"+": 1, "-": 1, "*": 2, "/": 2, "^": 3}
RIGHT_ASSOC = {"^"}


def tokenize(expr):
    tokens, num = [], ""
    for ch in expr:
        if ch.isdigit():
            num += ch
        else:
            if num:
                tokens.append(num)
                num = ""
            if ch in PREC or ch in "()":
                tokens.append(ch)
            elif not ch.isspace():
                raise ValueError(f"unexpected character {ch!r}")
    if num:
        tokens.append(num)
    return tokens


def to_postfix(tokens):
    out, ops = [], []
    for t in tokens:
        if t.isdigit():
            out.append(t)                              # operands go straight out
        elif t == "(":
            ops.append(t)
        elif t == ")":
            while ops and ops[-1] != "(":
                out.append(ops.pop())
            if not ops:
                raise ValueError("mismatched ')'")
            ops.pop()                                   # discard "("
        else:
            while (ops and ops[-1] != "(" and
                   (PREC[ops[-1]] > PREC[t] or
                    (PREC[ops[-1]] == PREC[t] and t not in RIGHT_ASSOC))):
                out.append(ops.pop())                   # stronger operators first
            ops.append(t)
    while ops:
        if ops[-1] == "(":
            raise ValueError("mismatched '('")
        out.append(ops.pop())
    return out


def eval_postfix(tokens):
    st = []
    for t in tokens:
        if t in OPS:
            if len(st) < 2:
                raise ValueError("not enough operands")
            b, a = st.pop(), st.pop()                   # order matters: a op b
            st.append(OPS[t](a, b))
        else:
            st.append(int(t))
    if len(st) != 1:
        raise ValueError("too many operands")
    return st[0]

I.7 Monotonic stack: next greater element


Keep a stack of indices whose values are decreasing from bottom to top — elements still waiting for a larger value to their right. When a new value x arrives, every waiting element smaller than x has just found its answer: pop them all, then push x. This is the sequential stack algorithm for the all nearest smaller (or larger) values problem, which runs in linear time. [22]


def next_greater(nums):
    ans = [-1] * len(nums)
    st = []                                  # indices; values decreasing bottom->top
    for i, x in enumerate(nums):
        while st and nums[st[-1]] < x:
            ans[st.pop()] = x                # x is the first greater to the right
        st.append(i)
    return ans                               # leftovers keep -1

print(next_greater([4, 5, 2, 25, 7, 3, 8]))  # [5, 25, 25, -1, 8, 8, -1]

I.8 A queue from two stacks


class TwoStackQueue:
    def __init__(self):
        self._in, self._out = [], []

    def enqueue(self, x):
        self._in.append(x)

    def dequeue(self):
        if not self._out:
            while self._in:                  # reverse 'in' into 'out'; each item moves once
                self._out.append(self._in.pop())
        if not self._out:
            raise IndexError("dequeue from empty queue")
        return self._out.pop()

q = TwoStackQueue()
for x in [1, 2, 3]:
    q.enqueue(x)
print(q.dequeue()); q.enqueue(4)
print(q.dequeue(), q.dequeue(), q.dequeue())   # 1 then 2 3 4


Two reversals restore FIFO order. Each element is pushed onto _in once, moved once, and popped from _out once, so every operation is O(1) amortised although a single dequeue may be Θ(n). [16]



I.9 Replacing recursion with an explicit stack


Depth-first search is naturally recursive; replacing the call stack with your own stack removes the recursion-depth limit. Sedgewick and Wayne set exactly this as an exercise (a nonrecursive DFS “with an explicit stack instead of recursion”). [24]


def dfs_iterative(graph, start):
    seen, order, st = set(), [], [start]
    while st:
        v = st.pop()
        if v in seen:
            continue                         # a vertex can be pushed more than once
        seen.add(v)
        order.append(v)
        for w in reversed(graph[v]):         # reversed: neighbours pop in list order
            if w not in seen:
                st.append(w)
    return order

g = {"A": ["B", "C"], "B": ["D"], "C": ["D", "E"], "D": [], "E": []}
print(dfs_iterative(g, "A"))                 # ['A', 'B', 'D', 'C', 'E']


def factorial_explicit(n):
    st, result = [], 1
    while n > 1:          # "call" phase: push pending multiplications
        st.append(n)
        n -= 1
    while st:             # "return" phase: pop and combine
        result *= st.pop()
    return result

print(factorial_explicit(5))                 # 120


DFS with this “push all neighbours, skip if seen” style is O(V + E) time and O(E) stack space in the worst case (a vertex may sit on the stack several times).

JReal-world applications



J.1 Operating systems and hardware: the call stack


Every thread of every process has a stack region in its address space holding the frames of active function calls; OSTEP lists code, heap and stack as the three main regions, with heap and stack placed at opposite ends so they can grow toward each other. [15] The processor supports it directly: on x86, push decrements the stack pointer and stores, pop loads and increments, and call pushes the return address. [14] Stack overflow — exceeding the fixed stack size, usually through runaway recursion — is a classic crash; the JVM reports it as StackOverflowError. [12][20]





J.2 Language runtimes and virtual machines


Many virtual machines are stack machines: instructions take operands from, and push results onto, an operand stack instead of naming registers. CPython’s bytecode works this way (dis documents each instruction by its effect on STACK), the JVM gives each frame a LIFO operand stack, and WebAssembly instructions interact with an implicit stack of values, labels and activation frames. [9][12][13] Stack code is compact and easy to generate from a parse tree — it is postfix notation.



J.3 Compilers, parsers, editors and linters


Parsing nested syntax is a stack problem: expression parsers use operator and operand stacks to honour precedence and associativity in O(n), and Dijkstra designed shunting-yard for an ALGOL 60 compiler. [17][21] The same bracket-matching logic runs in code editors (highlighting the matching bracket), linters, JSON/XML/HTML validators (matching open and close tags), and template engines.



J.4 Search and backtracking


Depth-first search, maze solving, flood fill, topological sorting and backtracking solvers (Sudoku, N-queens, regex engines with backtracking) all explore the most recently discovered option first — a stack, explicit or via recursion. [24] Large-scale systems prefer the explicit stack so that input size cannot crash the process through recursion depth. [8]



J.5 Databases: nested savepoints


SQL savepoints nest like a stack. In PostgreSQL, ROLLBACK TO SAVEPOINT s “implicitly destroys all savepoints that were established after” s — rolling back to a point discards everything pushed after it. [25]



J.6 Web and backend applications: undo/redo and navigation


Engineering illustration (our example)A text editor or design tool keeps two stacks of states (or of reversible commands). Every edit pushes onto the undo stack and clears the redo stack; undo pops from undo and pushes onto redo; redo does the reverse. A bounded deque(maxlen=…) caps memory by silently dropping the oldest history. Backend request handling uses the same nesting idea — middleware layers and with-blocks are entered in one order and exited in the reverse order. The coding problem P.3 #3 builds this editor.

def largest_rectangle(heights):
    st, best = [], 0                         # indices of increasing heights
    for i, h in enumerate(heights + [0]):    # sentinel 0 flushes the stack
        while st and heights[st[-1]] > h:
            height = heights[st.pop()]
            left = st[-1] + 1 if st else 0
            best = max(best, height * (i - left))

    return best

NAdvanced concepts



N.1 Monotonic stacks in depth


A monotonic stack keeps its contents sorted (increasing or decreasing) by popping anything that would break the order before each push. Four variants cover most problems: next greater to the right (decreasing stack, scan left→right), next smaller to the right (increasing stack), and the same two “to the left” (read the stack top after popping, before pushing). The underlying problem is called all nearest smaller values; it is solved in linear time sequentially, and Berkman, Schieber and Vishkin showed how to solve it efficiently in parallel. [22]





N.2 Queues and deques from stacks; min-queue


The two-stack queue (Section I.8) combined with the min-stack (I.5) gives a queue that reports its minimum in O(1) amortised: keep a min-stack for input and one for output, and the answer is the smaller of their two minima. This is the basis of the sliding-window minimum in CP-Algorithms. [16]



N.3 Worst-case O(1) array stacks


Amortised bounds allow an occasional Θ(n) push. Real-time systems can avoid it by incremental copying: when the array becomes half full, allocate the bigger array and copy two old items on every subsequent push, so the copy finishes before the old array fills. Each push then does O(1) work in the worst case, at the cost of keeping two arrays during the transition. (A standard de-amortisation technique; we present it as a design sketch.)



N.4 Persistent (immutable) stacks


Because a linked stack’s push never modifies existing nodes, an old head still describes the old stack after a push. Many versions can share their common tail: pushing 4 onto 3→2→1 and pushing 9 onto the same 3→2→1 gives two stacks that share three nodes. Functional languages implement their basic list type this way (a “cons list”), and undo histories can keep every version in O(1) extra space per operation.



N.5 Two stacks in one array, and stack machines


Two stacks can share one fixed array by growing toward each other from opposite ends — exactly the arrangement of heap and stack in a process address space (Figure J.1) — and overflow happens only when the total size exceeds the array. [15] Going further, an entire computer can be organised around a stack: the JVM and WebAssembly define their semantics this way, and compilers translate expression trees into stack code by a postorder traversal. [12][13]



N.6 Stacks and formal languages


A finite automaton plus one unbounded stack is a pushdown automaton, the machine model for context-free languages such as balanced brackets and programming-language grammars — the formal reason why nesting needs a stack, and why a regular expression without extensions cannot check balanced parentheses of arbitrary depth. Bauer and Samelson’s term Kellerautomat (“cellar automaton”) is a historical name for this machine. [19]

Conceptual answers

    

  1. Adding or removing at the end of an array touches one slot; at index 0 every other element must shift, costing Θ(n) per operation. Python documents pop(0)/insert(0, x) as O(n) for this reason. [5]
    2. 

  2. At exactly half full, push → grow (copy n), pop → shrink (copy n), push → grow… every operation becomes Θ(n). Halving only at one-quarter full leaves the new array half full, so Ω(capacity) operations separate any two resizes and the amortised cost stays O(1). [1][2]
    3. 

  3. Linked: hard real-time code that cannot tolerate a Θ(n) resize pause, or persistent stacks sharing structure. Array: almost everything else — better cache locality and less memory per item, which is why Python’s list is the default stack.
    4. 

  4. Each index is pushed exactly once (one push per iteration of the for) and every iteration of the while pops one index. An index cannot be popped more often than it was pushed, so total while iterations ≤ n. Total work = O(n) pushes + O(n) pops + O(n) failed tests = O(n).
    5. 

  5. 1 3 2: push 1, pop 1, push 2, push 3, pop 3, pop 2 ✓. 2 3 1: push 1, push 2, pop 2, push 3, pop 3, pop 1 ✓. 3 1 2 ✗: to output 3 first, 1 and 2 must both be on the stack with 2 above 1, so 2 must come out before 1. # 1. Remove adjacent duplicates
def remove_adjacent_duplicates(s):
    st = []
    for ch in s:
        if st and st[-1] == ch:
            st.pop()                         # the pair cancels
        else:
            st.append(ch)
    return "".join(st)

# 2. Decode string
def decode_string(s):
    st, cur, k = [], "", 0
    for ch in s:
        if ch.isdigit():
            k = k * 10 + int(ch)
        elif ch == "[":
            st.append((cur, k)); cur, k = "", 0   # save outer context
        elif ch == "]":
            prev, times = st.pop()
            cur = prev + cur * times
        else:
            cur += ch
    return cur

# 3. Undo / redo editor
class UndoRedo:
    def __init__(self):
        self.text, self.undo_st, self.redo_st = "", [], []

    def type(self, s):
        self.undo_st.append(self.text)
        self.text += s
        self.redo_st.clear()                 # new edit invalidates redo history

    def undo(self):
        if self.undo_st:
            self.redo_st.append(self.text)
            self.text = self.undo_st.pop()

    def redo(self):
        if self.redo_st:
            self.undo_st.append(self.text)
            self.text = self.redo_st.pop()

assert remove_adjacent_duplicates("abbaca") == "ca"
assert decode_string("3[a2[c]]") == "accaccacc"
ed = UndoRedo(); ed.type("a"); ed.type("b"); ed.undo(); ed.type("c"); ed.undo(); ed.redo()
assert ed.text == "ac"


Complexities: (1) Θ(n) time and space; (2) time proportional to the output length, stack O(nesting depth); (3) each operation O(1) stack work, but storing whole snapshots costs O(length of text) per edit — store reversible commands (inserted text + position) instead for large documents.



Engineering scenario — model answer

Why it crashes. Each [ makes the recursive parser call itself, pushing one frame on the call stack. 200,000 levels exceed Python’s recursion limit (default 1000, giving RecursionError) or, if someone raised the limit, overflow the C stack and kill the process — the Python docs warn that a too-high limit can crash the interpreter. [8][20] Either way an attacker controls the depth: a denial-of-service vector.


Fix. Rewrite the validator as an iterative parser with an explicit stack of open containers ([ or { plus parser state such as “expecting key”). Open → push, close → pop and check the type matches, end → stack empty — the bracket algorithm of Section I.4 generalised. The explicit stack lives on the heap, so depth no longer threatens the process.


Limits. Still cap nesting depth (for example 512 levels) and total document size, and reject early with HTTP 400/413; legitimate documents are rarely deeply nested, and the cap bounds memory per request. Stream the input so validation memory is O(depth) rather than O(size).


Costs. One pass over the input: Θ(n) time; stack memory O(d) with d ≤ the depth cap; each push/pop O(1) amortised with a Python list.
